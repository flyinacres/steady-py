# Review findings (verified, pending entry into development.md)

## Known bugs

- **One IPython line anywhere breaks manifest extraction for the whole notebook.** `generate.extract_manifest_from_file` joins every code cell into one source and calls `ast.parse` once, after blanking lines that start with `%` or `!`. A single `files = !ls`, `x = %timeit ...` or `df?` survives the blanking and fails the parse, so the notebook returns "Could not parse" and check and delta break (confirmed with a two-cell notebook). The blanking itself also turns valid Python invalid: a triple-quoted string whose closing line starts with `%`, a backslash continuation line starting with `% `, and a parenthesized condition whose last line starts with `!= b)` all parse before stripping and fail after (tested). Fix: parse per cell (the manifest lives in one cell), and replace the blanking with one shared helper.
- **A scan silently loses every import in a cell it can't parse.** `scanning.py` applies the same line-blanking (copy-pasted twice, a third copy is in `generate.py`) and, on `SyntaxError`, drops the cell with no diagnostic. A notebook with one magic in expression position loses that cell's imports while the report looks complete. This is false success; at minimum emit a diagnostic naming the cell.
- **A dropped connection during a PyPI fetch crashes the run.** `pypi._fetch_pypi_json` reads the response inside the try, but catches only `HTTPError`, `URLError`, `TimeoutError` and `JSONDecodeError`. Errors raised during the read (`http.client.RemoteDisconnected`, `IncompleteRead`, SSL errors) escape, so one transient drop exits 2 instead of reporting `NETWORK_ERROR`. Fix: catch `OSError` (which already covers `URLError` and `TimeoutError`) and `http.client.HTTPException`.
- **Local-module detection depends on an incidental import.** `localmodules._found_in_dir` calls `importlib.machinery.PathFinder`, but the module imports only `importlib.util`, which does not bind `importlib.machinery` (AttributeError in a clean 3.12 interpreter). It works today only because `installed.py` imports `importlib.metadata`. If that changes, the `except Exception` swallows the error and every local module silently reports as not found. Fix: `import importlib.machinery`.
- **Transitive checks evaluate platform markers against the machine running check.** `drift._marker_environment` overrides only the Python version and extra and takes the rest from `default_environment()`. Running check on Windows against a Kaggle or Colab notebook drops Linux-only requirements (torch's `nvidia-*` dependencies are marked `platform_system == "Linux"`) and includes Windows-only ones. Fix: set `sys_platform`, `platform_system`, `os_name` and `platform_machine` from the target when it is Kaggle or Colab; keep the host values for a local target.
- **OpenCV variant detection has its own view of what's installed.** `resolution.resolve_opencv_variant` runs `pip list` in a subprocess on every call, unmemoized, even though the caller already holds `frozen_env` from the run's single `pip freeze`. Two independent sources of installed state can disagree. Fix: derive the variant from `frozen_env`. Worse than duplication: `resolve_pypi_package_and_extras` first takes `pkg_dist_map[imp][0]` (`resolution.py:282`), which follows `sys.path` order and is correct, then overwrites it for `cv2` with `resolve_opencv_variant` (line 284). With base-env `opencv-python-headless 4.8.0.76` and a `--system-site-packages` venv holding `opencv-python 4.10.0.84`, the active cv2 is 4.10.0.84 but the pin is `opencv-python-headless==4.8.0.76`, no warning (venv reviewer confirmed; a user-site split on plain Python behaves the same, read from code). The fix recorded here earlier ("derive the variant from `frozen_env`") is wrong, since `frozen_env` holds both names. Fix: use `pkg_dist_map['cv2'][0]` when present and keep the variant heuristic only as a fallback when nothing is installed; conda-forge stubs still need the capability check in the Conda environments entry.
- **Replacing a prior setup cell can discard user code.** `generate.is_prior_setup_cell` matches any code cell that assigns `STEADY_PY_MANIFEST` anywhere, including inside a function (`ast.walk`), and `write_locked_notebook` drops the whole cell with no warning. With `--in-place` a user's scratch cell that copied the assignment is lost from the original. The content match is deliberate (untagged pasted cells must be replaced), so the fix is a warning when a removed untagged cell contains other statements, not dropping the match.
- **A package that can't be looked up becomes a confirmed conflict.** `drift.resolve_transitive_graph` excludes root pins not found on PyPI, but `_PyPIResolutionProvider.find_matches` returns no candidates for any transitive package whose fetch status isn't FOUND. Resolvelib then raises `ResolutionImpossible`, reported as a CONFIRMED conflict. Triggers: a transitive dependency hosted only on a custom index (NVIDIA's index packages), or, more likely, a transient network error on any transitive fetch. "Could not look it up" should be reported as unverifiable.
- **Extras promotion is nondeterministic and records at most one extra.** `resolution.resolve_pypi_package_and_extras` iterates the submodule `set` and stops at the first tail name that matches a `Provides-Extra`, so with two matches the chosen extra depends on hash randomization and can differ between runs. Name matching also misses most extras, since extras rarely share names with submodules, and pip does not record which extras were requested at install time. A sounder heuristic: an extra counts as installed if its `Requires-Dist` entries are all present.
- **Display text is parsed back as data.** `analyze.analyze_batch_repository` recovers a package name from `dep.comment_text.split()[1]` when `dep.name` is empty, and `generate.py` filters auxiliary entries with `aux.comment_text.startswith("\n# ---")`. Both are strings the tool built earlier in the same run, so they can't be tampered with, but rewording a comment would silently misfile packages. Carry structured fields (name, status) instead of parsing rendered text.
- **The setup markdown cell is recognized by its heading text.** `generate.is_prior_setup_cell` falls back to matching `SETUP_MARKDOWN_HEADING`, which is unprotected notebook text. If a user edits the heading and the cell has lost its managed tag, the old setup cell survives as a stale duplicate. Low severity: the managed tag is the primary signal.
- **In a live kernel, snapshot pins nothing that is actually installed.** `localmodules.resolve_local_module` uses an unrestricted `find_spec` in a live kernel and returns "root_dir" for any importable module not in `notebook_dir`, and resolution checks local modules before distributions. Reproduced through `endpoints.scan` with the kernel check forced true: `import packaging` from site-packages came back as a `local_module` comment. The live-kernel API is the non-engineer path. development.md's known-bug entry ("Live-kernel local modules outside `notebook_dir` are all tagged `root_dir`") understates this and should be rewritten. Fix: in a live kernel, a module whose origin belongs to an installed, non-editable distribution is never a local module.

### Guards and install harvesting

- **A guarded install line erases every import in its cell.** In a cell containing `import pandas` and `if IN_COLAB:` followed by an indented `%pip install xyz`, the line blanking leaves an empty if-body, `ast.parse` raises `SyntaxError`, and the scan returns zero imports for the cell with no diagnostic (confirmed by running `scanning.extract_import_occurrences_from_source` and `extract_imports_from_sources_full`). The standard guarded-install pattern silently removes real dependencies.
- **A guarded import loses its guard when the pip name differs.** `resolution.build_unified_timeline` computes `is_guarded = pkg_name in guarded_set`, where `pkg_name` is the install line's pip name (`python-dotenv`, `scikit-learn`) and `guarded_set` holds import names (`dotenv`, `sklearn`). The lookup never matches, so the package is installed although its import is guarded (verified by running). The same key mismatch drops submodules (`submodules_map` is keyed by import name), so extras promotion never fires for such packages. The same comparison in `build_unified_timeline` step 2 makes `import paddle` alongside `%pip install paddlepaddle-gpu` produce two manifest entries, doubling every finding for that package (custom-index reviewer, read from code).
- **A guarded install line is installed unconditionally.** `magics.harvest_pip_install_occurrences` matches lines with a regex and has no scope information, so `if IN_COLAB: %pip install x` is treated as a top-level install (verified by running). Raw installs and index URL flags are harvested the same way, regardless of guard (read from code).
- **A variable install becomes a package named `$pkg`.** `%pip install $pkg` is harvested literally (verified by running). A static scan cannot know the value; this should be a warning, not a package.
- **Several install forms are not detected, and nothing warns.** `!python -m pip install`, `!{sys.executable} -m pip install`, `os.system(...)`, `subprocess` calls and `get_ipython().system(...)` are all missed (verified by running). `PIP_INSTALL_PATTERN` recognizes only `%pip`, `!pip` and bare `pip`/`pip3`. Also missed: `%uv pip install` (IPython 9 ships a `%uv` magic; confirmed not harvested) and `!conda run -n base pip install ...` (conda reviewer confirmed).
- **Mutually exclusive branches collapse to the last pin.** `magics.resolve_pip_occurrences` is last-wins by canonical name, which is correct for sequential reinstalls but wrong when two branches install the same package with different pins or flags; only a warning remains (read from code).
- **Non-literal dynamic imports get a generic warning with no guard state.** Only `importlib.import_module` (including aliased bindings) and `__import__` are recognized (read from code).
- **Guard tagging is coarse.** `TYPE_CHECKING`, `if __name__ == "__main__"` and platform flags are treated like `try/except ImportError`, and alternatives have no group identity or intent class (read from code).
- **A wrapper helper that shells out to pip loses the guard at its call site** (read from code).
- **A second live resolution path carries its own guard logic.** `resolution.build_manifest_entries` and `build_dependency_objects` are used by `generate.generate_universal_manifest` (`generate.py:345`, the `--universal` path) and duplicate the guard and resolution logic of `build_unified_timeline`, so `--universal` output can diverge from per-notebook output. Unverified lead from the editables review: `--universal` drops DIRECT_REFERENCE URLs that per-notebook `raw_installs` keep. It also takes pins from `frozen_env` and ignores install-line versions, flags and guards (local-version reviewer, read from code). Only `process_package_requirements` is test-only. Route `--universal` through the same timeline, and remove the test-only helper or move its tests onto the live path. (Corrects an earlier version of this entry that called the whole path test-only.)
- **`--opt=value` pip flags are silently dropped.** `magics.harvest_pip_install_occurrences` splits arguments on spaces and matches index flags exactly, so `--index-url=https://...` and `--extra-index-url=...` fail the match and are then skipped as generic flags. Both it and `harvest_index_urls_from_sources` return no URL (confirmed); the space-separated form works. Cell 2 then searches public PyPI and fails.
- **PEP 508 direct references are split into three entries.** `%pip install "pkg @ git+https://..."`, the form pip accepts, yields packages `pkg` and `@` plus a detached raw install of the URL, because `split()` runs before quotes are handled (confirmed). The unquoted form is a pip error and should be flagged, not registered.
- **`%%writefile` cells with leading blank lines are scanned as notebook code.** `scanning.classify_cell_source` checks only the first line, so a blank first line makes the cell PYTHON and its imports (`import torch` in the test) become notebook dependencies (confirmed). IPython's `TransformerManager` strips leading blank lines and runs the cell as `run_cell_magic('writefile', ...)`, so IPython accepts this form.
- **Single pip flags and raw-install index flags are dropped.** `PIP_SINGLE_FLAGS` (`--no-deps`, `--pre`, `--force-reinstall`, ...) are discarded: `%pip install --no-deps xformers==0.0.28` yields `flags: []` (confirmed), so the runner installs xformers' dependencies, including a different torch. Losing `--pre` is mostly harmless since an exact `==` pin matches a prerelease. Raw installs also lose their line's index flags: `git+https://... --index-url https://x/simple` keeps only the URL (confirmed), which breaks when the package's dependencies come from that index. Fix: carry flags that change what gets installed (`--no-deps`, index flags) per pin and per raw install.

### Cell 2 runtime (`runtime.install`)

- **Pins with extras never pass the already-installed check.** A promoted name such as `packaging[foo]` is written to the manifest as-is, and `importlib.metadata.version("packaging[foo]")` raises `PackageNotFoundError` (confirmed). The `except Exception: pass` hides it, so pip reruns on every execution, `any_install_performed` fires the restart warning, and the package never enters the drift baseline. Stripping the brackets is not enough: the base package being present doesn't mean the extra's dependencies are. Either check the extra's `Requires-Dist` entries or let pip handle bracketed names (pip is idempotent and correct for extras). The same line has a second bug; see the string-equality entry below.
- **A pin that drifts after being verified still counts as verified.** If package A passes and a later install changes its version, the loop prints a drift line, but `passed_count` still includes A and the summary reads "Setup complete! All N/N dependencies verified." This is false success. Packages outside the manifest (for example, a platform package an install downgrades) aren't tracked at all, because the baseline holds only manifest packages already visited. Fix: snapshot `importlib.metadata.distributions()` before and after the loop, report the diff, and re-verify every manifest pin before printing the success line. The same fix covers raw installs that move pinned versions after they were verified. The re-verification needs three outcomes, not two: verified, failed, and installed-but-restart-required (see the user-site entry below), or it will mislabel correct user-site installs as failures.
- **The already-installed check uses string equality, not PEP 440.** `runtime.install` tests `current_ver == ver` (`runtime.py:88`), so a public pin on a platform build (`%pip install torch==2.8.0` on Colab's `2.8.0+cu126`) prints "Installing", pip reports "Requirement already satisfied", and the run shows "installed successfully" plus a needless restart note every time (reviewer confirmed with `demo-loc`). Fix: `SpecifierSet(f"=={ver}").contains(current)`; `==1.0+cu118` still rejects `1.0+cu121` (verified), so local pins are not loosened. Fix together with the extras entry above, same line.
- **A user-site install counts as verified while the kernel still runs the old version.** `runtime.install` treats pip's exit code 0 as success (`runtime.py:110`) and reads the version afterward (line 116) without comparing it to the pin. When the kernel's site-packages isn't writable (an all-users Python on Windows, a shared JupyterHub or course server, an admin-owned venv), pip prints "Defaulting to user installation", and `site.py` adds the user site to `sys.path` only if it existed at interpreter start, so on a first install the kernel can't see the new version. Reviewer confirmed on an all-users 3.11 and a root-owned `--system-site-packages` 3.12 venv: "tabulate==0.9.0 installed successfully" and "All 1/1 dependencies verified" while `importlib.metadata` and the module report 0.10.0; rerunning without a restart repeats the success ("already satisfied"). The closing note says "may need to restart", and HELP.md says a restart is needed only "if you've already run other cells", so a runner following the recommended flow skips it. Call sites: the pin branch (`runtime.py:110-127`), the `raw_installs` branch (150), the summary lines (162, 171), the HELP.md restart entry. Fix: after exit 0, compare the in-process version to the pin (PEP 440); if the matching distribution sits in `site.getusersitepackages()` and that directory isn't on `sys.path`, report "installed to your user folder: restart the kernel, then rerun Cell 2" and don't count it as verified.
- **Cell 2's helper install can succeed and still leave `import steady_py` failing or importing an older helper.** The bootstrap checks only pip's exit code (`generate.py:227`) and then imports (232); the user-site mechanism above applies. Case (a), new: an admin-owned `--system-site-packages` venv without steady-py; pip installs into `~/.local`, the import fails with `ModuleNotFoundError`, and HELP.md's advice (`%pip install steady-py` and retry) returns "Requirement already satisfied" and the same error, a loop. Case (b): an admin-preinstalled 0.0.45 with a Cell 2 pinning 0.0.46; 0.0.46 lands in the user site and `install()` runs from 0.0.45 with nothing printed, a new trigger for development.md's "Cell 2 can silently use a different steady-py version" (that fix covers it only if the version comparison runs regardless of pip's exit code). Reviewer confirmed both. Fix: if the import fails or the imported version differs from the pin, print one instruction (restart the kernel and rerun Cell 2), and update the HELP.md entry to match.

### Creator environment capture

- **A failed `pip freeze` produces an empty "verified" manifest and exit 0.** On a nonzero return code, `installed.get_installed_environment` returns `({}, [])`, indistinguishable from an empty environment, and skips the PEP 610 overlay; the only signal is a `logger.warning` that `--quiet` suppresses. Every import becomes a "not found" comment, Cell 2 shows `'dependencies': []` under "VERIFIED ENVIRONMENT DEPENDENCIES", and the runner sees "All 0/0 dependencies verified." Triggers: a uv venv (no pip module; confirmed by the reviewer), a UnicodeEncodeError on a non-ASCII editable path under a Windows ANSI code page (simulated), and pip's own freeze crashes (pip 20.2.x raised AssertionError on flit editables). `results.Environment` has no failure field. Fix: a typed failure carrying pip's stderr; endpoints map it to exit 2 with nothing written. Call sites: `get_installed_environment`, `endpoints.detect_environment` (scan, snapshot, batch), `results.Environment`.
- **Packages frozen as `name @ file://...` are dropped, even when that version is on PyPI.** `split_frozen_pin` returns version `None` for every `@` pin, and `resolve_pypi_package_and_extras` sends local URLs to a `system_path` comment (confirmed: `six @ file:///...whl` pinned nothing; the reviewer saw "STATUS: Clean", exit 0, no warnings). Verified real-world trigger: conda-built packages carry `direct_url.json`, so pip freeze in a fresh Miniconda env lists e.g. `certifi @ file:///opt/conda/conda-bld/...` (conda/conda#11580), and core packages vanish for Anaconda creators. Windows Anaconda shows the same pattern as `file:///C:/b/abs_.../croot/<pkg>_.../work` (second reviewer, confirmed through `generate.apply_output_to_notebook`: only the conda-built package vanished, Cell 2 told the creator to "publish" sympy, and the validation report carried no finding or notice). Fix: carry the installed version with the URL. Detect conda-built packages (the env's `conda-meta/` records are ground truth, and conda-forge dist-infos' `INSTALLER` reads `conda`, verified by the conda reviewer; key detection on `INSTALLER`/`conda-meta`, not on `file://` URLs, since some conda dist-infos have no `direct_url.json` at all, see the OpenCV entry) and pin those as name==version with a notice. An unexplained local `file://` reference is reported to the creator as a candidate, not auto-pinned, since a private project can share a PyPI name. Call sites: `split_frozen_pin`, `get_installed_environment`, `_read_direct_reference_pins`, both branches of `resolve_pypi_package_and_extras`, `build_auxiliary_tool_entries`, `build_writefile_tool_entries`.
- **The direct-reference overlay can replace the active package's pin with a shadowed copy's.** `_read_direct_reference_pins` walks `distributions()` across all of `sys.path`, skips distributions without `direct_url.json`, and `setdefault`s among the rest; `get_installed_environment` then applies `frozen.update()` unconditionally. Import and pip use the first copy on `sys.path`; this code keeps the first copy that has `direct_url.json`. Reviewer confirmed: six 1.17.0 active (import, `importlib.metadata`, pip freeze all agree) recorded as a shadowed `six @ file:///...1.16.0`. With a remote URL the stale source goes into `raw_installs` and the runner installs the old version. Real-world trigger (untested): an all-users Anaconda install where pip falls back to the user site. Another second source of installed state. Fix: mark every canonical name on first sight, with or without `direct_url.json`, and ignore later duplicates. The overlay also replaces lines pip freeze already formatted correctly: diffed against pip 24.0's `direct_url_as_pep440_direct_reference`, ours drops `#subdirectory=` and archive hashes (`#sha256=`; the code has no hash handling). If freeze is kept, the alternative fix is to let freeze's lines win and fill only names it cannot express (editables).
- **`--full-freeze` embeds private local paths in the shared notebook.** `get_installed_environment` returns freeze output verbatim, and `generate` `repr()`s it into `FULL_FREEZE_FALLBACK`: editable paths (`-e /Users/.../ClientAcme/...`) and `file://` URLs land in Cell 2 (reviewer confirmed). This breaks the development.md promise that no private path leaks into a shared notebook. The list sits outside the hashed manifest, and `runtime.py` never reads it despite the "FALLBACK" name (confirmed). Consider removing the flag rather than sanitizing it; otherwise build the list from parsed entries, reducing local references to name==version with a note.
- **VCS direct references lose `#subdirectory=`.** `_read_direct_reference_pins` builds `vcs+url@commit` and ignores the `subdirectory` key of `direct_url.json` ("subdirectory" appears nowhere in the code). The runner installs the repository root, which fails or installs a different project. `_direct_source_key` also strips the fragment, so `same_direct_source` and the merge loop in `generate.generate_production_blueprint` treat two packages from different subdirectories of one monorepo as one source and drop the second (confirmed by a second reviewer: `raw_installs` held only `alpha`, `runtime.install` printed "All 1/1 dependencies verified" and `beta` was not importable; `TestSameDirectSource` has no subdirectory case). This also hits the common Kaggle pycocotools install from cocoapi (`#subdirectory=PythonAPI`) whenever the notebook lacks its own install line. Fix: append `#subdirectory=` when present and include it in the source key, while still ignoring ref, egg and hash.
- **Non-PEP 440 versions are stored with a stray `=`.** Freeze prints `legacypkg===0.8.1ubuntu1` (still true in pip 26.2.1), and every `split("==", 1)` stores the version as `=0.8.1ubuntu1`. Low harm. Call sites: `get_installed_environment`, `split_frozen_pin`, `resolution.py` (two sites).
- **A directory scan tells the creator that installed git and conda packages are missing.** `analyze.analyze_batch_repository` sends every comment entry except `platform_pseudo_module`, `build_tool` and `local_module` into `missing_packages`, so direct-reference and `system_path` packages are reported as "not found installed ... run 'pip install <package>'" by `reporting.format_console_report` (called from `cli.run_scan_directory`) and `format_json_batch_report`. Following that advice replaces a git build with whatever PyPI hosts under the name. Confirmed for the analysis (`missing_packages == {'zzq-remote': ..., 'sympy': ...}`); console text read from code. Root cause: batch re-derives meaning from `is_comment` plus an exclusion list instead of the status, the batch-versus-single drift pattern again. Fix: an explicit status-to-bucket mapping with a "non-PyPI source" bucket.
- **Cell 2 comments claim a direct-reference package "is installed from the non-standard sources list" when nothing installs it.** `installed.direct_reference_note` hardcodes the clause, and it is called from four places (`resolution.py` lines 157, 215, 305, 333: auxiliary tool, `%%writefile` script, guarded, direct reference), but only direct-reference entries reach `raw_installs` (confirmed by a second reviewer; the existing guarded test asserts `raw_installs` is empty). False user-facing text, worst for `%%writefile` scripts later run via `!python train.py`. Fix: the note states provenance only; the installation clause comes from the code that actually adds the spec.

### Editable installs and local modules

- **An in-tree editable's own dependencies never reach the manifest.** `resolve_pypi_package_and_extras` returns a LOCAL_MODULE comment as soon as `resolve_local_module` finds the name, before any distribution lookup (the SYSTEM_PATH and guarded branches also return comments), and no code reads `distribution(...).requires` for an editable. Reviewer confirmed: a project `in-flat` depending on `six>=1.10`, installed with `pip install -e`, imported from a notebook in the project: `dependencies: []`, "Clean", exit 0; the runner saw "Setup complete! All 0/0 dependencies verified." and then `ModuleNotFoundError: No module named 'six'`. Pip resolves hard dependencies only for packages it installs, and the runner can't install this one. Call sites: the three branches of `resolve_pypi_package_and_extras`, reached from `build_unified_timeline` and `build_dependency_objects` (`--universal`), and the separate `local_mods_detected` computation in `analyze.build_single_notebook_report`. Fix: when an import maps to an editable distribution, pin its `Requires-Dist` from the installed environment, evaluating markers for the target platform, and exclude the `editables` shim that hatchling and pdm inject.
- **Directory and single-file modes classify the same import differently, and check calls the wrong answer clean.** `root_dir` is derived per entry point: `endpoints._analyze` passes the notebook's parent for a file, while `analyze.analyze_batch_repository` and `generate.generate_universal_manifest` pass the target directory (confirmed in code). `resolve_local_module` tests directories before any installed-distribution evidence, so an in-tree editable imported from `notebooks/sub_nb.ipynb` is SYSTEM_PATH in single-file mode but a `root_dir` local module in directory mode; `check --root-dir .` reports "Clean" because `check_local_modules` only tests file existence, and the runner in `notebooks/` gets `ModuleNotFoundError` (reviewer confirmed). The outcome also flips between src and flat layouts. The same assumption treats a plain, non-editable folder under `root_dir` as importable from subdirectory notebooks. Fix: derive `root_dir` in one place; a module found under `root_dir` (not `notebook_dir`) that belongs to an editable distribution is that editable, not a local module; a plain folder under `root_dir` counts only if it is on the notebook's import path.
- **An editable or custom-path import produces no warning and exit 0.** SYSTEM_PATH exists only as a comment entry; nothing turns it into a `DiagnosticEvent`, and `cli._run_exit_code` counts only parse and write outcomes. Reviewer confirmed: a notebook importing eleven editable packages got JSON `warnings: []`, "Clean", exit 0, with the only trace in Cell 2 comments. Call sites: the SYSTEM_PATH and guarded-with-local-`direct_url` branches of `resolve_pypi_package_and_extras`, the `direct_url` branches of `build_auxiliary_tool_entries` and `build_writefile_tool_entries`, `cli._run_exit_code`. (The batch "not found installed" half is the batch-bucketing entry under Creator environment capture.) Fix: a typed diagnostic per editable import ("your in-development package; runners can't install it"), counted as needs-attention (exit 1), with its own batch bucket.
- **The import-to-distribution join misses hatchling, pdm, legacy and `conda develop` editables.** What decides it is whether the build backend writes `top_level.txt`: `packages_distributions()` maps setuptools (finder, src, strict), uv and legacy editables but not hatchling or pdm (both modes); legacy editables are then missing from `frozen_env` (freeze's `-e` line is skipped and there is no `direct_url.json`); `conda develop` has no metadata at all. All come out "not found via pip-freeze" with JSON status `pinned`, while setuptools editables come out SYSTEM_PATH (reviewer confirmed). A renamed hatchling fork (`tabulate-ron` providing `tabulate`) is reported not found and the batch advice says `pip install tabulate`, which silently shadows the fork with the PyPI release. `build_writefile_tool_entries` uses only `IMPORT_TO_PYPI_MAP`, so the same import is "not found in active env" inside `%%writefile` and SYSTEM_PATH in a normal cell (another duplicated-logic instance). Fix: one join helper that resolves an unmapped import by its `find_spec` origin, matched against editable source directories (the `direct_url` URL, or the `.egg-link` target for legacy); an origin outside any distribution gets a "custom path" status.
- **A VCS editable is reported as an unshareable local path.** `pip install -e git+https://...` freezes as `-e git+...@<HEAD>`, but its `direct_url.json` holds the local checkout's `file://` URL, and the code prefers `direct_url.json` (reviewer confirmed). The checkout may carry uncommitted changes, so pinning HEAD automatically isn't safe either; report it to the creator as a candidate (git source plus commit, valid if pushed and clean).
- **A data folder next to the notebook hides an installed package.** `localmodules._found_in_dir` uses `PathFinder.find_spec`, which treats a folder without `__init__.py` as a namespace package, so a `datasets/` folder holding only `train.csv` makes `resolve_local_module('datasets', notebook_dir)` return `notebook_dir` (confirmed). `import datasets` (Hugging Face) in that notebook becomes a local-module comment and is never pinned, while at runtime the installed regular package wins. Folders named `data`, `datasets` and `models` are everyday layouts for the audience. Fix: a namespace-only match counts as a local module only when no installed distribution provides the name (distribution evidence first, as in the single-join fix).

### Local version (+cuXXX) builds

- **Local-version pins skip every PyPI check, so a real conflict reports clean.** `drift.run_pin_checks` replaces all direct checks for a `+`-tagged pin with one heuristic `unverifiable_custom_index` finding (`drift.py:425`), and `drift.resolve_transitive_graph` drops it from the root requirements (`drift.py:339`, "not on PyPI by definition"). The premise is wrong: `2.8.0+cu126` is the public release 2.8.0 plus a build tag, and under PEP 440 `==2.8.0` matches it (verified). Reviewer confirmed against live PyPI: pins `torch==2.8.0+cu126` and `torchvision==0.22.0` produce no findings (the resolver picks torch 2.7.0), while `torch==2.8.0` gives two CONFIRMED conflicts. Yanked, removed, stale and Python-support checks on the public release are skipped too. At runtime the torchvision install pulls torch 2.7.0 over the platform build, and with the drift-counting bug the run can end "Setup complete" (read from code). Call sites: `run_pin_checks`, `resolve_transitive_graph`, `generate_production_blueprint` (same predicate), baseline keys. Fix: check and resolve local pins as `name==Version(v).public`, stating that build-specific dependencies (`nvidia-*`) stay unverified. Existing manifests recorded `unverifiable_custom_index`, so newly visible findings must be classed as not checked at generation, not new, or every old notebook exits 1.
- **`custom_sourced` is decided by the wrong rule, so public packages are labeled as the author's private packages.** Two triggers. Build tags: `generate.generate_production_blueprint` puts every `+`-tagged pin into `custom_sourced` (`generate.py:175`), the list for genuinely private packages, so when such a pin fails `runtime.install` says the package is "custom-specified by the notebook's author (not on public PyPI)... contact the author", even when the same release is installed as another CUDA build (reviewer confirmed: `demo-loc==1.0+cu118` against installed `1.0+cu121`). `run_pin_checks` similarly says "installed from a custom index" for Colab and Kaggle preinstalled builds with no install line. The manifest has no field separating "build-tagged public release" from "not on PyPI". Fix: a separate hashed manifest field for build-tagged pins, and distinct runtime output for a public-version match with a different build. Network errors: the same loop treats any status other than FOUND as custom, so a transient `NETWORK_ERROR` for a public package at snapshot is sealed into the hashed `custom_sourced` list permanently (reviewer confirmed: `requests` with the project endpoint patched to fail gave `custom_sourced: ['requests']` while the drift side correctly recorded an error). Check never re-derives the list. This loop is another independent copy of the "is this on PyPI" decision; derive `custom_sourced` from the shared predicate or per-pin findings, never from a failed lookup.
- **`--universal` requirements cannot install any `+cu` build.** `magics.harvest_cell_magics_and_commands` files `-f`/`--find-links` values under `extra_index_urls` (`magics.py:233`), and `generate.generate_universal_manifest` writes every harvested URL as `--extra-index-url` (`generate.py:340`) with local-labeled pins from `frozen_env`. A find-links page is not an index: pip reports "versions: none" for it as an index URL and installs from it as `-f` (reviewer confirmed with a locally served page), and because `pip install -r` is atomic nothing in the file installs. Colab-preinstalled local pins get no URL and no warning in the file. Cell 2 for the same notebook is correct (`flags: ['-f', url]`), so this is another divergence of the `--universal` path. Call sites: `harvest_cell_magics_and_commands`, `analyze.select_primary_index_url` and the "Primary Download Index" report line, `generate_universal_manifest`. Fix: keep find-links as `--find-links`, and list local pins with no source in the file's header warning.
- **Cell 1 lists pip flag names as download URLs.** `resolution.build_dependency_entries` records `(dep.specifier, dep.flags)` (`resolution.py:509`), raw flag tokens included, and `generate_production_blueprint` renders every token as "Download index" (`generate.py:141`), producing "Download index: `--index-url`" followed by the URL; `-f` pages are also labeled "index" (reviewer confirmed). The test-only `process_package_requirements` passes clean URLs, so its tests pass while production fails, concrete evidence for the dead-duplicate entry. Fix: carry typed `(flag, url)` pairs.

### Custom-index packages

- **A custom-index pin whose project also exists on PyPI is reported as removed, and it disables transitive checking for every pin.** "Is this on PyPI?" is decided by the local-version tag or by project existence, never by the pin's own flags or by whether that version is on PyPI. `drift.check_yanked_or_removed` reports "version missing, project found" as REMOVED; `resolve_transitive_graph` excludes a root only when the whole project is missing, so the pin stays, gets no candidates and raises `ResolutionImpossible` at the root, abandoning the graph; `classify_against_baseline` demotes only NOT_FOUND_ON_PYPI (confirmed in code). Reviewer confirmed with `%pip install paddlepaddle-gpu==3.0.0 -i https://www.paddlepaddle.org.cn/...` (PyPI stops at 2.6.2): confirmed conflict, REMOVED and stale findings, `custom_sourced: []`, check exits 1 on every run, and the chardet, idna and urllib3 findings for `requests` disappear once paddle is added. A genuinely removed PyPI version also abandons the graph at the root (read from code). Call sites: `drift.run_pin_checks`, `check_yanked_or_removed`, the root loop of `resolve_transitive_graph`, the `custom_sourced` loop in `generate.generate_production_blueprint`, `classify_against_baseline`, `runtime.install` (misses the custom-source message). The "on PyPI?" decision is made in at least four places with four rules.
- **A version from the environment is paired with an index flag from an unversioned install line.** When the line has no `==`, `resolution.build_unified_timeline` takes the version from `frozen_env` and copies `occ.flags` unconditionally. The Kaggle case: `!pip install -q torch torchvision --index-url https://download.pytorch.org/whl/cu121` is a no-op ("already satisfied") on the platform's `torch==2.6.0+cu124`, and the manifest pairs `2.6.0+cu124` with the cu121 index (reviewer confirmed). PyTorch 2.6.0 ships only cu118, cu124, cu126 and cpu builds, so the runner's install fails and is told to "contact the author", who was never warned: `missing_hardware_index` fires only when flags are empty, and check exits 0 (runtime failure read from pip semantics and PyTorch's wheel matrix). Nothing ever queries the recorded index, so check also stays clean after an index drops a file (e.g. purged nightlies; read from code). Call sites: `build_unified_timeline` (PIP branch), `build_dependency_entries` (warning condition), the local-tag early `continue` in `run_pin_checks`. Under "pin what's installed", the index must match where the installed build came from; when that can't be established, report the pin rather than pair it with the notebook's flag.

### Conda environments

- **conda-forge OpenCV yields an uninstallable, wrong-variant pin and false "removed" and conflict findings.** conda-forge's opencv recipe writes stub dist-infos `opencv_python-{v}` and `opencv_python_headless-{v}` with only METADATA (the conda version, e.g. `5.0.0`) and INSTALLER (`conda`): no `direct_url.json`, no RECORD, so pip freeze prints plain `opencv-python==5.0.0` and the `file://` entry never catches them. `resolution.resolve_opencv_variant` checks headless first (`resolution.py` lines 435 to 442, confirmed), and the recipe installs both stubs in every build, GUI builds included, so the pin is always headless. The version is taken verbatim, but PyPI has only four-part releases (`5.0.0.93`), and `==5.0.0` doesn't match under PEP 440. Reviewer confirmed with `import cv2` and `cv2.imshow(...)`: pin `opencv-python-headless==5.0.0`, "[removed] ... no longer exists on PyPI" (it never existed), a false unresolvable-graph conflict, check exits 1 on every run, and the runner's install fails with "No matching distribution". The headless-first bias also hits pip users with both `opencv-python` and `opencv-python-headless` installed (common when two dependencies want different variants), giving the runner a build where `cv2.imshow` fails. Call sites: `resolve_opencv_variant`, `resolve_pypi_package_and_extras` (single-file and `--universal`), `build_writefile_tool_entries` (pins `opencv-python==5.0.0` via `IMPORT_TO_PYPI_MAP`), the wording in `drift.check_yanked_or_removed`. Fix: when the OpenCV distribution's INSTALLER is `conda`, map it to the newest PyPI release with the same first three components and tell the creator; choose the variant by build capability, not by which dist-infos exist.
- **Conda-family install commands other than `conda install` produce no notice.** `magics.CONDA_INSTALL_PATTERN` matches only `(%conda|!conda|conda) install`. `!mamba install`, `%mamba install` (IPython 9 ships `%mamba` and `%micromamba`), `!micromamba install`, `!conda env update -f environment.yml` and the condacolab recipe (`condacolab.install()` then `!mamba install`, the standard Colab route for OpenMM and rdkit tutorials) all return zero notices, warnings and packages (reviewer confirmed; `!mamba install` and `%mamba install` reproduced). `!conda install --file requirements.txt` gets only the generic notice, while the pip `-r` equivalent gets a share-this-file warning. Fix: one table of conda front-ends (conda, mamba, micromamba, `%` and `!` forms) and subcommands (install, create, env create/update), with `--file`/`-f` handled like pip's `-r`.

### Directory runs

- **Directory runs scan and rewrite notebooks inside any virtual environment not named `.venv`, `venv` or `env`.** `analyze.iter_notebook_paths` prunes by name only (`DEFAULT_IGNORED_DIRS`, `constants.py:24`), so `python -m venv myenv` inside the project (the usual tutorial name) is walked into site-packages, where wheels ship notebooks (papermill 23, nbdime 59, holoviews 308). Reviewer confirmed with `myenv` holding jupyter and papermill: scan analyzed 24 notebooks, listed "ggplot" as missing with "run 'pip install <package>'" and "STATUS: Ready"; `snapshot --output` wrote 23 `_merged` files into site-packages; `snapshot --in-place` rewrote installed package files (hash changed, manifest inserted), invalidating pip's RECORD hashes, exit 0. Those notebooks' imports also flow into the repository summary and `--universal` (read from code). This contradicts the README's promise that virtual environments are skipped. Call sites: `iter_notebook_paths` (feeds scan, snapshot, `--universal`, and check on a directory at `endpoints.py:306`), `DEFAULT_IGNORED_DIRS`, README line 168. Fix: prune any directory containing `pyvenv.cfg` or `conda-meta/`, and any `site-packages` or `dist-packages` directory; keep the name list as a fast path.

### Pinning, delta and output stability

- **Version operators are stripped into invalid or untested pins.** `resolution.build_unified_timeline` computes `v_clean = occ.version_spec.lstrip("=<>!~")` and the manifest writes `==`. `%pip install torch>=2.0,<3` becomes `torch==2.0,<3` (an invalid specifier), and `numpy~=1.26` becomes `numpy==1.26` although 1.26.4 is installed (confirmed). Preserving the author's bounds would defeat reproducibility. Pin the installed version when it satisfies the author's spec (`packaging.specifiers.SpecifierSet`), report when it doesn't, and keep an explicit `==` as written.
- **An import resolves to an arbitrary distribution when several provide its top-level name.** `resolve_pypi_package_and_extras` takes `pkg_dist_map[imp][0]`, and `imp` is the top-level module. For namespace packages this is plainly wrong: `from google.cloud import storage` pinned `protobuf` (confirmed). Two installed variants of one module also occur in practice (three distributions provide `cv2` in a stock container; only the separate OpenCV path handles that case). Resolve against the full dotted import using `dist.files`, and report when the match is still ambiguous rather than pick one.
- **Delta ignores everything but name and version.** `delta.compute_delta` compares name to version, Python, GPU and baseline only, so changes to flags (`--extra-index-url`, `--find-links`), `raw_installs`, `custom_sourced` and `local_modules` report "no changes" while the manifest is rewritten (read from code).
- **Editable installs vanish without a warning.** `-e`/`--editable` is in `PIP_VALUE_FLAGS`, so pass 2 skips the flag and its path before the VCS/path check; `%pip install -e ./mypkg` yields no occurrence, no raw install and no diagnostic (confirmed). `-r` at least emits an `external_requirement` warning.
- **Snapshot rewrites an unchanged notebook.** `create_managed_cells` assigns random cell IDs (`uuid.uuid4()`), and `generated_at`, and therefore `dependency_hash`, change on every run, so an in-place snapshot of an unchanged notebook always produces a diff. Fix: reuse existing managed cell IDs, and either skip the write when the delta is empty or carry `generated_at` forward. Which depends on what `generated_at` is meant to record.
- **Imports not found in the environment are labeled `pinned`.** `resolve_pypi_package_and_extras` returns status `pinned` for a not-found import rendered as a comment (confirmed: `baz` → `pinned`, `is_comment=True`), so scan JSON consumers see a missing package as pinned.
- **Batch reports lose each notice's notebook, and cell numbers match nothing the user sees.** `DiagnosticEvent` has no path, and `analyze.analyze_batch_repository` dedupes with `if notice not in summary.magic_notices` (lines 287 to 299, confirmed; the same pattern collapses warnings, dynamic warnings and promotions), so two notebooks with the same `!conda install` line print one "Cell 1 uses 'conda install'" naming no notebook (reviewer confirmed; the JSON keeps them per notebook), and pip external-requirement warnings lose attribution the same way. Cell numbers count code cells only, and `magics.py` numbers from 0 in `harvest_pip_install_occurrences` (line 50) and from 1 in `harvest_cell_magics_and_commands` (line 237), so two functions in one module give the same cell different numbers, neither matching the notebook position (a conda line in cell 5 after three markdown cells reports as "Cell 2"). Fix: carry the notebook path on every aggregated event, dedupe by (path, event), and number cells by notebook position everywhere.

### Code health

- **Import parameters are typed `Any`, and result classes carry lossy tuple-unpacking shims.** Eight import parameters in `accelerator.py` and `resolution.py` are `Any`. `TimelineResult`, `ExtractionResult` and `HarvestResult` define `__iter__` for legacy unpacking; no production code uses it (the only unpacking is of `ExtractionResult` in `test_steady_py_fixtures.py`), and the shims convert `DiagnosticEvent` objects to strings. Remove the shims, migrate the tests, type the parameters. Same cleanup as the duplicate resolution path entry (only `process_package_requirements` is test-only).
- **Broad `except Exception` hides logic errors.** About 20 production sites (accelerator, resolution, runtime, util, localmodules, scanning, drift). Two recorded bugs are exactly this: the swallowed `importlib.machinery` AttributeError and the swallowed extras `PackageNotFoundError`. Audit per site: narrow catches around our own and stdlib calls; keep broad catches around third-party probes (torch, TensorFlow, CUDA initialization), logged at debug with `exc_info`.
- **The package logger never propagates, even as a library.** `__init__.py` sets `propagate = False` at import, so a host that configures only the root logger gets nothing from steady-py (a host can still attach handlers to the `steady_py` logger directly). The stated reason, avoiding double printing, applies only once the CLI attaches its console handler. Move `propagate = False` into `configure_console()`.

## Design gaps

- Optional dependencies that are never imported (openpyxl, gcsfs, spaCy models) are seen only if the notebook has an install line. There is no candidate detection. Package metadata can supply candidates without a hardcoded list: pandas declares openpyxl and gcsfs in its extras, so an imported package plus an installed package named in one of its extras is a candidate. spaCy models are declared in no metadata and need a different signal.
- There is no creator warning about guarded alternatives, and no runtime report of which alternatives are present. A clean run cannot verify the untaken branch.
- It is unknown whether a platform baseline (Kaggle or Colab preinstalled packages) exists; candidate lists need one.
- Guard, unresolved and install-only status exist only as Cell 2 comments; the manifest has no protected record of them. `check` and the planned report of which guarded alternatives are present need them as manifest fields.
- Pins come from the interpreter running the CLI. If a creator installs steady-py with pipx or `uv tool`, or runs it from conda base while the kernel uses another env, every pin describes the wrong environment, and nothing warns (unverified lead; the natural next review boundary).
- No runtime policy for a pin whose public release matches the platform's but whose build tag differs (manifest `torch==2.8.0+cu121`, platform `2.8.0+cu126`). Accepting risks a CUDA mismatch; reinstalling means a multi-GB download over the platform build. The runtime counterpart of "pin what's installed"; needs an explicit decision.

## Principles

- Cell 2 is never edited as text; changes go through the tool, which records their provenance. The tool will never infer every dependency, so the creator must be able to correct and extend the manifest: creator declarations are inputs to the tool, stored in the manifest with provenance, and carried forward by every snapshot. (Revises "Cell 2 is never hand-edited", which left manifest errors unfixable.)
- Report to the creator is the default for candidates and unknown targets. Never auto-add. Each report should be actionable through a creator declaration.
- Hard dependencies are out of scope. Optional dependencies are in scope. This holds only where pip installs the package and so resolves its dependencies; for a package the runner cannot install (an editable, the creator's own code), its `Requires-Dist` entries are in scope and are pinned from the installed environment.
- Comments and other display text are never a source of truth. Anything the tool needs later is a structured, hashed manifest field; anything it needs within a run is carried as a typed field, not parsed back out of rendered text.
- The recorded commit wins over a notebook's own unpinned VCS line. When the notebook installs `git+...@main` (or no ref) and the environment records a commit, pin the commit, consistent with pinning the installed version over an author's `>=` bound. This reverses the current development.md spec (a remote direct reference goes to `raw_installs` "unless the notebook's own install line names the same source"), which must be updated.
- Each decision has one owner. Entry points (single file, batch, `--universal`, live kernel, check) differ only in how they gather inputs and render outputs, never in how they classify, resolve or judge. Most findings trace to decisions re-derived in several places; consolidation follows after more material is gathered.

## Proposed fixes

- **Parse magics into Python, then scan one AST.** Transform `%` and `!` lines, `x = !cmd` and `obj?` into `get_ipython()` calls before parsing. IPython's `TransformerManager` (`IPython.core.inputtransformer2`) does this; IPython is not a base dependency, so use it when importable and fall back to a small transformer of our own. Install commands then inherit the guard state of their enclosing block. Also fixes the stripping bugs above and replaces the three copies of the blanking code.
- **Join pip names to import names through installed metadata.** Use the run's `packages_distributions()` (`pkg_dist_map`) first and `IMPORT_TO_PYPI_MAP` as a fallback, so guards and submodules carry across name differences. Decide which wins when an unconditional install meets a guarded import (the defect above implies the guard does).
- **Harvest literal shell-outs; warn on the rest.** After the AST change, `os.system`, `subprocess` and `get_ipython().system` calls with literal pip arguments are recordable with their guard state. Emit a `DiagnosticEvent` only for non-literal arguments, including `%pip install $pkg` and non-literal dynamic imports.
- **Parse pip arguments the way pip does.** Tokenize with `shlex.split`, use an option table that accepts both `--opt value` and `--opt=value`, and parse requirement tokens with `packaging.requirements.Requirement` (already a base dependency). The magics-to-AST change doesn't cover this, since `run_line_magic` still receives the raw argument string.
- **Read installed state from `importlib.metadata`, not `pip freeze` text.** One source, first match on `sys.path` wins, versions always carried (including for direct references), PEP 610 data read directly. Addresses the failed-freeze, `file://`, shadowing, `#subdirectory=` and `===` bugs at the root, and removes the dependency on pip being present. Freeze output has changed across pip releases (direct references as `name @ url` since 20.1; setuptools and wheel no longer excluded on Python 3.12+ since 24.1; legacy versions deprecated in 24.1), so parsing it ties results to the creator's pip version. Precondition: differential testing against `pip freeze` on the Docker tiers (plain 3.11, Kaggle, Colab), a conda env and a uv env, accounting for every difference (freeze's exclusions, name spelling, shadowing order, legacy `.egg-link` editables) before switching. The new reader is a second implementation of pip's internal `direct_url_as_pep440_direct_reference`, so it must reproduce VCS commit, `#subdirectory=` and archive-hash formatting, and the differential test must include direct references (VCS with subdirectory, archives with hashes, conda-built `file://`, editables). Keep freeze afterward as a test oracle only. Editable divergences to cover: PEP 660 editables (all backends, uv) agree apart from `direct_url.json` key order; legacy `setup.py develop` has no `direct_url.json` and must be detected through `.egg-link`/`easy-install.pth`; a VCS editable freezes as `-e git+...@<HEAD>` while `direct_url.json` holds a local `file://` URL; `conda develop` is visible only to `find_spec`; `packages_distributions()` returns duplicates, so dedupe before diffing.
- **One `root_dir` derivation and one import-to-distribution join.** Derive `root_dir` in one place for every entry point, and resolve every import (normal cell, `%%writefile`, auxiliary tool) through one helper: `packages_distributions()` first, then the `find_spec` origin matched against editable source directories, with local-module classification only after distribution evidence is exhausted.
- **Build a decision inventory before rearchitecting.** List each decision the tool makes (local or installed, which distribution, guarded or not, which pin, is it a problem, which exit code) and every place in the code that makes it. It sizes the consolidation, serves as a checklist so a fix reaches every copy until the copies are merged, and is a good boundary for an external review pass.
- **One shared "is this pin from PyPI" predicate, per-version root exclusion, and index lookups.** A pin is non-PyPI if it carries an index flag, a local tag, or a version absent from PyPI; every site (`run_pin_checks`, `check_yanked_or_removed`, `resolve_transitive_graph`, `classify_against_baseline`, `custom_sourced`, `runtime.install`) uses the same predicate. Exclude roots per version, not per project, so one bad pin never abandons the graph. At snapshot and at check, look each flagged pin up on its recorded index through the simple API (PEP 691/503) and report when it is absent.
- **Creator declarations: vouched additions and overrides, maintained by the tool.** A separate manifest section, covered by the hash, holding creator-declared items with provenance (user-supplied, timestamp, tool version, optional name and reason). Edits made through the tool (CLI verb and in-notebook API) recompute the hash; raw text edits are still reported as tampered, so the hash distinguishes tool-mediated vouching from hand edits (integrity, not identity). Validate at declaration time as far as possible: package and version exist on PyPI, the version supports the manifest's Python, and it resolves with the rest of the manifest (`pip install --dry-run --report` gives a real resolver answer without installing); check re-validates declared pins like any others. Snapshot carries declarations forward and reports conflicts with evidence (declared `torch==2.3.1`, environment now 2.4.0) for the creator to resolve, never overriding silently; a declared package the tool later detects on its own is marked redundant. Start with add-a-package and override-a-derived-pin; removing derived items or suppressing findings can come later, if at all. Runtime messages can then truthfully say "added by the notebook's author" for declared items. Covers what inference cannot: plugin and backend dependencies (the settled scope boundary), optional dependencies never imported, spaCy models, dynamic imports.
- **Deferred: keep alternative pins per branch.** Cell 2 installs one environment, so keeping both pins needs a way to say which branch applies at runtime. Depends on guard identity and creator declarations; until then, report to the creator.

## Reviewed and rejected

- `_RUN_CACHES` as a memory leak or thread hazard: caches are created once at import (four decorated functions) and nothing in the tool runs concurrently.
- `silence_fd2_stderr` swallowing other threads' output: intentional, and scoped to the brief CUDA probe window.
- Optional-dependency detection as a rabbit hole requiring a hardcoded knowledge base: the objection targets auto-adding, which the principles already exclude, and extras metadata supplies candidates without a hardcoded list.
- Unpinned packages evading drift checks: an install line without a version is pinned from the environment (`%pip install foo` became `foo==1.0`), and anything not installed becomes a comment, never a versionless dependency (confirmed). The underlying gap, statuses recorded only as comments, is already under Design gaps.
- Replacing `error: Optional[str]` on per-notebook results with Success|Failure types: most `Optional` fields are unrelated to failure (`delta` only when a manifest exists, `written_path` None when nothing was written), directory runs need one uniform per-notebook list, and the in-notebook API audience would face `isinstance` checks. Revisit before the first release if the API shape changes anyway.
- `is_prior_setup_cell` mixing read-phase analysis into the write phase: deciding which cells to replace requires reading them, and it parses only the cell under test with no scan state. Its real defects are recorded under Known bugs.
