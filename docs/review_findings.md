# Review findings

What is wrong and why, one entry per finding, by matrix ID. Each entry carries its evidence and its fix; entries are deleted once fixed. Settled state, tests and the step that fixes each are in test_triage_matrix.md; the plan is in fix_plan.md.

## Known bugs

- **K5. Transitive checks evaluate platform markers against the machine running check.** `drift._marker_environment` overrides only the Python version and extra and takes the rest from `default_environment()`. Running check on Windows against a Kaggle or Colab notebook drops Linux-only requirements (torch's `nvidia-*` dependencies are marked `platform_system == "Linux"`) and includes Windows-only ones. Fix: set `sys_platform`, `platform_system`, `os_name` and `platform_machine` from the target when it is Kaggle or Colab; keep the host values for a local target.
- **K7. Replacing a prior setup cell can discard user code.** `generate.is_prior_setup_cell` matches any code cell that assigns `STEADY_PY_MANIFEST` anywhere, including inside a function (`ast.walk`), and `write_locked_notebook` drops the whole cell with no warning. With `--in-place` a user's scratch cell that copied the assignment is lost from the original. The content match is deliberate (untagged pasted cells must be replaced), so the fix is a warning when a removed untagged cell contains other statements, not dropping the match.
- **K8. A package that can't be looked up becomes a confirmed conflict.** `drift.resolve_transitive_graph` excludes root pins not found on PyPI, but `_PyPIResolutionProvider.find_matches` returns no candidates for any transitive package whose fetch status isn't FOUND. Resolvelib then raises `ResolutionImpossible`, reported as a CONFIRMED conflict. Triggers: a transitive dependency hosted only on a custom index (NVIDIA's index packages), or, more likely, a transient network error on any transitive fetch. "Could not look it up" should be reported as unverifiable.
- **K9. Extras promotion is nondeterministic and records at most one extra.** `resolution._promoted_extra` iterates the submodule `set` and stops at the first tail name that matches a `Provides-Extra`, so with two matches the chosen extra depends on hash randomization and can differ between runs. Name matching also misses most extras, since extras rarely share names with submodules, and pip does not record which extras were requested at install time. A sounder heuristic: an extra counts as installed if its `Requires-Dist` entries are all present.
- **K10. Display text is parsed back as data.** `analyze.analyze_batch_repository` recovers a package name from `dep.comment_text.split()[1]` when `dep.name` is empty, and `generate.py` filters auxiliary entries with `aux.comment_text.startswith("\n# ---")`. Both are strings the tool built earlier in the same run, so they can't be tampered with, but rewording a comment would silently misfile packages. Carry structured fields (name, status) instead of parsing rendered text.
- **K11. The setup markdown cell is recognized by its heading text.** `generate.is_prior_setup_cell` falls back to matching `SETUP_MARKDOWN_HEADING`, which is unprotected notebook text. If a user edits the heading and the cell has lost its managed tag, the old setup cell survives as a stale duplicate. Low severity: the managed tag is the primary signal.
- **D7. The live-session recipe is clunky.** Getting the cells out of `steady_py.snapshot()` in a notebook takes `result.notebooks[0].cells.markdown` and `.code`. A helper that displays both cells (or a rich display of the result in IPython) would cut the README recipe to two lines, which matters for the non-engineer audience.

### Guards and install harvesting

- **G4. A variable install becomes a package named `$pkg`.** `%pip install $pkg` is harvested literally (verified by running). A static scan cannot know the value; this should be a warning, not a package.
- **G5. Several install forms are not detected, and nothing warns.** `!python -m pip install`, `!{sys.executable} -m pip install`, `os.system(...)` and `subprocess` calls are all missed (verified by running). So is a one-line shell conditional (`!if [ -d x ]; then pip install y; fi`), whose `;` split leaves `then pip install y`; it needs step 1.4's shell tokenization, and then counts as guarded. `PIP_INSTALL_PATTERN` recognizes only `%pip`, `!pip` and bare `pip`/`pip3`. Also missed: `%uv pip install` (IPython 9 ships a `%uv` magic; confirmed not harvested) and `!conda run -n base pip install ...` (conda reviewer confirmed).
- **G7. Non-literal dynamic imports get a generic warning with no guard state.** Only `importlib.import_module` (including aliased bindings) and `__import__` are recognized (read from code).
- **G8. Guard tagging is coarse.** `TYPE_CHECKING`, `if __name__ == "__main__"` and platform flags are treated like `try/except ImportError`, and alternatives have no group identity or intent class (read from code).
- **G10. A second live resolution path carries its own guard logic.** `resolution.build_manifest_entries` and `build_dependency_objects` are used by `generate.generate_universal_manifest` (`generate.py:345`, the `--universal` path) and duplicate the guard and resolution logic of `build_unified_timeline`, so `--universal` output can diverge from per-notebook output. Unverified lead from the editables review: `--universal` drops DIRECT_REFERENCE URLs that per-notebook `raw_installs` keep. It also takes pins from `frozen_env` and ignores install-line versions, flags and guards (local-version reviewer, read from code). Only `process_package_requirements` is test-only. Route `--universal` through the same timeline, and remove the test-only helper or move its tests onto the live path. (Corrects an earlier version of this entry that called the whole path test-only.)
- **G11. `--opt=value` pip flags are silently dropped.** `magics.harvest_pip_install_occurrences` splits arguments on spaces and matches index flags exactly, so `--index-url=https://...` and `--extra-index-url=...` fail the match and are then skipped as generic flags. Both it and `harvest_index_urls_from_sources` return no URL (confirmed); the space-separated form works. Cell 2 then searches public PyPI and fails.
- **G12. PEP 508 direct references are split into three entries.** `%pip install "pkg @ git+https://..."`, the form pip accepts, yields packages `pkg` and `@` plus a detached raw install of the URL, because `split()` runs before quotes are handled (confirmed). The unquoted form is a pip error and should be flagged, not registered.
- **G14. Single pip flags and raw-install index flags are dropped.** `PIP_SINGLE_FLAGS` (`--no-deps`, `--pre`, `--force-reinstall`, ...) are discarded: `%pip install --no-deps xformers==0.0.28` yields `flags: []` (confirmed), so the runner installs xformers' dependencies, including a different torch. Losing `--pre` is mostly harmless since an exact `==` pin matches a prerelease. Raw installs also lose their line's index flags: `git+https://... --index-url https://x/simple` keeps only the URL (confirmed), which breaks when the package's dependencies come from that index. Fix: carry flags that change what gets installed (`--no-deps`, index flags) per pin and per raw install.
- **G16. An install line with extras produces an invalid pin.** `magics.harvest_pip_install_occurrences` splits each token at the first of `<>=!~;[#`, so the extra becomes the version spec: `"tabulate[widechars]"` yields spec `[widechars]`. `resolution.build_unified_timeline` then strips only leading operator characters (`lstrip("=<>!~")`) and writes the rest as the version (confirmed): `tabulate[widechars]` pins `tabulate==[widechars]`, `tabulate[widechars]==0.8.10` pins `tabulate==[widechars]==0.8.10`, and `"tabulate[widechars]>=0.8"` pins `tabulate==[widechars]>=0.8`. The explicit-spec branch overrides the installed version, so the environment's correct pin is discarded. Generation-time validation reports a confirmed `removed` finding ("tabulate==[widechars] no longer exists on PyPI"), and at run time pip rejects the specifier ("Extras after version"), so Cell 2 reports a failed install for a package that was installed correctly (both confirmed). The extra itself is lost, so its dependencies are never pinned. The corpus scan finds an extra on about 260 of 1068 distinct install lines (heuristic count), mostly `transformers[...]` and `qdrant-client[...]`. Call sites: `harvest_pip_install_occurrences`, the explicit-spec branch of `build_unified_timeline`. Fix: parse requirement tokens with `packaging.requirements.Requirement` (fix_plan.md, step 1.4), carry the extras onto the entry name as `pkg[extra]`, and apply P1's specifier rules. Fix together with R1, since a correctly named `pkg[extra]` pin then hits that runtime bug.
- **G17. An install line whose name isn't in canonical form is reported twice, and header rows are reported as nameless dependencies.** `analyze.build_single_notebook_report` computes `scan_res.harvested_pkgs - timeline_pkgs`, but `timeline_pkgs` is canonicalized and `harvested_pkgs` holds the names as typed. Any name with an underscore, a dot or an uppercase letter survives the subtraction and goes to `resolution.build_auxiliary_tool_entries` as well as the timeline. Confirmed with `%pip install typing_extensions Absentpkgzz` (lowercase `absentpkgzz` and `packaging` come out once):
  1. Scan JSON lists each package twice, once from the timeline and once as `auxiliary_tool`, plus a nameless dependency whose comment is Cell 2's `# --- AUXILIARY TOOL INSTALLS ---` header. A `%%writefile` cell likewise yields a nameless `writefile_script` entry for its header row (confirmed).
  2. Cell 2 repeats both packages under that header. `typing_extensions` is pinned and also commented as installed but not pinned.
  3. A directory scan lists installed `typing_extensions` as both matched and missing, and reports a missing package named `---`, which is `split()[1]` of the header comment (K10, now with a visible trigger).

  The same subtraction is absent in `generate.py:355` (`--universal`), which passes all harvested packages, another copy of the decision. Call sites: `analyze.py:189-190`, `resolution.build_auxiliary_tool_entries`, `analyze.analyze_batch_repository`, `generate.py:355`. Fix: canonicalize both sides of the subtraction. Header rows should be rendering, not `DependencyEntry` objects, so they can't reach reports.
- **G18. A trailing comment on an install line is harvested word by word as packages.** `!pip install timm # kaggle doesnt have it` yields packages `timm`, `kaggle`, `doesnt`, `have` and `it`, and `%pip install -U -q "google-genai>=2.9.0"  # 2.0 for Interactions API` yields `2.0`, `for`, `Interactions` and `API`, with non-canonical words also duplicated as above (confirmed). The creator's notebook runs correctly, because IPython hands the line to a shell, where `#` at the start of a word begins a comment. The corpus has 99 such lines, mostly in the Gemini cookbook. Fix: tokenize install lines as the shell does before parsing (fix_plan.md, step 1.4); a `#` inside a word (`url#egg=x`) is not a comment.
- **G19. Combined short flags hide `-r`.** `%pip install -qr requirements.txt` makes `requirements.txt` a package and gives no `external_requirement` warning (confirmed); `-q -r requirements.txt` works. pip's optparse reads `-qr file` and `-rfile` as `-q -r file`. The corpus has 48 such lines. Fix: expand short-flag clusters as optparse does, in the same pip-argument parser.
- **G20. Rare install-line forms are read differently from pip.** `--only-deps pkg` (pip 25+) installs only pkg's dependencies, but pkg is pinned. An unquoted `numpy<2` is a shell redirect from a file named `2`, so bash fails the line, while steady-py pins `numpy` unbounded. A wheel under a Kaggle utility-script path (`/kaggle/usr/lib/notebooks/...`) gets no Kaggle notice. Each appears in at most one corpus notebook.
- **D5. A folder scan reports a package named `---`.** Scanning a folder containing `tests/fixtures/unit/magic_sink.ipynb` lists `---` among the packages not resolvable via pip-freeze. The directory-scan symptom of G17.

### Cell 2 runtime (`runtime.install`)

- **R1. Pins with extras never pass the already-installed check.** A promoted name such as `packaging[foo]` is written to the manifest as-is, and `importlib.metadata.version("packaging[foo]")` raises `PackageNotFoundError` (confirmed). The `except Exception: pass` hides it, so pip reruns on every execution, `any_install_performed` fires the restart warning, and the package never enters the drift baseline. Stripping the brackets is not enough: the base package being present doesn't mean the extra's dependencies are. Either check the extra's `Requires-Dist` entries or let pip handle bracketed names (pip is idempotent and correct for extras). The same line has a second bug, R3.
- **R2. A pin that drifts after being verified still counts as verified.** If package A passes and a later install changes its version, the loop prints a drift line, but `passed_count` still includes A and the summary reads "Setup complete! All N/N dependencies verified." This is false success. Packages outside the manifest (for example, a platform package an install downgrades) aren't tracked at all, because the baseline holds only manifest packages already visited. Fix: snapshot `importlib.metadata.distributions()` before and after the loop, report the diff, and re-verify every manifest pin before printing the success line. The same fix covers raw installs that move pinned versions after they were verified. The re-verification needs three outcomes, not two: verified, failed, and installed-but-restart-required (R4), or it will mislabel correct user-site installs as failures.
- **R3. The already-installed check uses string equality, not PEP 440.** `runtime.install` tests `current_ver == ver` (`runtime.py:88`), so a public pin on a platform build (`%pip install torch==2.8.0` on Colab's `2.8.0+cu126`) prints "Installing", pip reports "Requirement already satisfied", and the run shows "installed successfully" plus a needless restart note every time (reviewer confirmed with `demo-loc`). Fix: `SpecifierSet(f"=={ver}").contains(current)`; `==1.0+cu118` still rejects `1.0+cu121` (verified), so local pins are not loosened. Fix together with R1, same line.
- **R4. A user-site install counts as verified while the kernel still runs the old version.** `runtime.install` treats pip's exit code 0 as success (`runtime.py:110`) and reads the version afterward (line 116) without comparing it to the pin. When the kernel's site-packages isn't writable (an all-users Python on Windows, a shared JupyterHub or course server, an admin-owned venv), pip prints "Defaulting to user installation", and `site.py` adds the user site to `sys.path` only if it existed at interpreter start, so on a first install the kernel can't see the new version. Reviewer confirmed on an all-users 3.11 and a root-owned `--system-site-packages` 3.12 venv: "tabulate==0.9.0 installed successfully" and "All 1/1 dependencies verified" while `importlib.metadata` and the module report 0.10.0; rerunning without a restart repeats the success ("already satisfied"). The closing note says "may need to restart", and HELP.md says a restart is needed only "if you've already run other cells", so a runner following the recommended flow skips it. Call sites: the pin branch (`runtime.py:110-127`), the `raw_installs` branch (150), the summary lines (162, 171), the HELP.md restart entry. Fix: after exit 0, compare the in-process version to the pin (PEP 440); if the matching distribution sits in `site.getusersitepackages()` and that directory isn't on `sys.path`, report "installed to your user folder: restart the kernel, then rerun Cell 2" and don't count it as verified.
- **R5. Cell 2's helper install can succeed and still leave `import steady_py` failing or importing an older helper.** The bootstrap checks only pip's exit code (`generate.py:227`) and then imports (232); the user-site mechanism above applies. Case (a), new: an admin-owned `--system-site-packages` venv without steady-py; pip installs into `~/.local`, the import fails with `ModuleNotFoundError`, and HELP.md's advice (`%pip install steady-py` and retry) returns "Requirement already satisfied" and the same error, a loop. Case (b): an admin-preinstalled 0.0.45 with a Cell 2 pinning 0.0.46; 0.0.46 lands in the user site and `install()` runs from 0.0.45 with nothing printed, a new trigger for D2 (that fix covers it only if the version comparison runs regardless of pip's exit code). Reviewer confirmed both. Fix: if the import fails or the imported version differs from the pin, print one instruction (restart the kernel and rerun Cell 2), and update the HELP.md entry to match.
- **D2. Cell 2 can silently use a different steady-py version.** If `pip install steady-py==<version>` fails, Cell 2 warns and still runs `import steady_py`. An already-installed, different version (a leftover, another notebook's setup in the same session) then runs `install()` with only the earlier warning as a trace. Fix: compare the imported version with the pin.
- **D3. Every install failure gets the same advice.** `install()` reports each failure's pip output, but the closing troubleshooting block always suggests checking internet access first, whatever the cause (a bad wheel, a timeout, a wrong Python). Cause-specific advice needs its own design pass.
- **D6. Cell 2's troubleshooting advice undoes the pin.** After a failure, `install()` suggests `!pip install <pkg>` with no version, which installs the newest release rather than the author's. It should suggest the exact version first (HELP.md already explains it that way).

### Creator environment capture

- **E4. `--full-freeze` embeds private local paths in the shared notebook.** `get_installed_environment` returns freeze output verbatim, and `generate` `repr()`s it into `FULL_FREEZE_FALLBACK`: editable paths (`-e /Users/.../ClientAcme/...`) and `file://` URLs land in Cell 2 (reviewer confirmed). This breaks the development.md promise that no private path leaks into a shared notebook. The list sits outside the hashed manifest, and `runtime.py` never reads it despite the "FALLBACK" name (confirmed). Consider removing the flag rather than sanitizing it; otherwise build the list from parsed entries, reducing local references to name==version with a note.

### Local version (+cuXXX) builds

- **LV1. Local-version pins skip every PyPI check, so a real conflict reports clean.** `drift.run_pin_checks` replaces all direct checks for a `+`-tagged pin with one heuristic `unverifiable_custom_index` finding (`drift.py:425`), and `drift.resolve_transitive_graph` drops it from the root requirements (`drift.py:339`, "not on PyPI by definition"). The premise is wrong: `2.8.0+cu126` is the public release 2.8.0 plus a build tag, and under PEP 440 `==2.8.0` matches it (verified). Reviewer confirmed against live PyPI: pins `torch==2.8.0+cu126` and `torchvision==0.22.0` produce no findings (the resolver picks torch 2.7.0), while `torch==2.8.0` gives two CONFIRMED conflicts. Yanked, removed, stale and Python-support checks on the public release are skipped too. At runtime the torchvision install pulls torch 2.7.0 over the platform build, and with the drift-counting bug the run can end "Setup complete" (read from code). Call sites: `run_pin_checks`, `resolve_transitive_graph`, `generate_production_blueprint` (same predicate), baseline keys. Fix: check and resolve local pins as `name==Version(v).public`, stating that build-specific dependencies (`nvidia-*`) stay unverified. Existing manifests recorded `unverifiable_custom_index`, so newly visible findings must be classed as not checked at generation, not new, or every old notebook exits 1.
- **LV2. `custom_sourced` is decided by the wrong rule, so public packages are labeled as the author's private packages.** Two triggers. Build tags: `generate.generate_production_blueprint` puts every `+`-tagged pin into `custom_sourced` (`generate.py:175`), the list for genuinely private packages, so when such a pin fails `runtime.install` says the package is "custom-specified by the notebook's author (not on public PyPI)... contact the author", even when the same release is installed as another CUDA build (reviewer confirmed: `demo-loc==1.0+cu118` against installed `1.0+cu121`). `run_pin_checks` similarly says "installed from a custom index" for Colab and Kaggle preinstalled builds with no install line. The manifest has no field separating "build-tagged public release" from "not on PyPI". Fix: a separate hashed manifest field for build-tagged pins, and distinct runtime output for a public-version match with a different build. Network errors: the same loop treats any status other than FOUND as custom, so a transient `NETWORK_ERROR` for a public package at snapshot is sealed into the hashed `custom_sourced` list permanently (reviewer confirmed: `requests` with the project endpoint patched to fail gave `custom_sourced: ['requests']` while the drift side correctly recorded an error). Check never re-derives the list. This loop is another independent copy of the "is this on PyPI" decision; derive `custom_sourced` from the shared predicate or per-pin findings, never from a failed lookup.
- **LV3. `--universal` requirements cannot install any `+cu` build.** `magics.harvest_cell_magics_and_commands` files `-f`/`--find-links` values under `extra_index_urls` (`magics.py:233`), and `generate.generate_universal_manifest` writes every harvested URL as `--extra-index-url` (`generate.py:340`) with local-labeled pins from `frozen_env`. A find-links page is not an index: pip reports "versions: none" for it as an index URL and installs from it as `-f` (reviewer confirmed with a locally served page), and because `pip install -r` is atomic nothing in the file installs. Colab-preinstalled local pins get no URL and no warning in the file. Cell 2 for the same notebook is correct (`flags: ['-f', url]`), so this is another divergence of the `--universal` path. Call sites: `harvest_cell_magics_and_commands`, `analyze.select_primary_index_url` and the "Primary Download Index" report line, `generate_universal_manifest`. Fix: keep find-links as `--find-links`, and list local pins with no source in the file's header warning.
- **LV4. Cell 1 lists pip flag names as download URLs.** `resolution.build_dependency_entries` records `(dep.specifier, dep.flags)` (`resolution.py:509`), raw flag tokens included, and `generate_production_blueprint` renders every token as "Download index" (`generate.py:141`), producing "Download index: `--index-url`" followed by the URL; `-f` pages are also labeled "index" (reviewer confirmed). The test-only `process_package_requirements` passes clean URLs, so its tests pass while production fails, concrete evidence for G10. Fix: carry typed `(flag, url)` pairs.

### Custom-index packages

- **CI1. A custom-index pin whose project also exists on PyPI is reported as removed, and it disables transitive checking for every pin.** "Is this on PyPI?" is decided by the local-version tag or by project existence, never by the pin's own flags or by whether that version is on PyPI. `drift.check_yanked_or_removed` reports "version missing, project found" as REMOVED; `resolve_transitive_graph` excludes a root only when the whole project is missing, so the pin stays, gets no candidates and raises `ResolutionImpossible` at the root, abandoning the graph; `classify_against_baseline` demotes only NOT_FOUND_ON_PYPI (confirmed in code). Reviewer confirmed with `%pip install paddlepaddle-gpu==3.0.0 -i https://www.paddlepaddle.org.cn/...` (PyPI stops at 2.6.2): confirmed conflict, REMOVED and stale findings, `custom_sourced: []`, check exits 1 on every run, and the chardet, idna and urllib3 findings for `requests` disappear once paddle is added. A genuinely removed PyPI version also abandons the graph at the root (read from code). Call sites: `drift.run_pin_checks`, `check_yanked_or_removed`, the root loop of `resolve_transitive_graph`, the `custom_sourced` loop in `generate.generate_production_blueprint`, `classify_against_baseline`, `runtime.install` (misses the custom-source message). The "on PyPI?" decision is made in at least four places with four rules.
- **CI2. A version from the environment is paired with an index flag from an unversioned install line.** When the line has no `==`, `resolution.build_unified_timeline` takes the version from `frozen_env` and copies `occ.flags` unconditionally. The Kaggle case: `!pip install -q torch torchvision --index-url https://download.pytorch.org/whl/cu121` is a no-op ("already satisfied") on the platform's `torch==2.6.0+cu124`, and the manifest pairs `2.6.0+cu124` with the cu121 index (reviewer confirmed). PyTorch 2.6.0 ships only cu118, cu124, cu126 and cpu builds, so the runner's install fails and is told to "contact the author", who was never warned: `missing_hardware_index` fires only when flags are empty, and check exits 0 (runtime failure read from pip semantics and PyTorch's wheel matrix). Nothing ever queries the recorded index, so check also stays clean after an index drops a file (e.g. purged nightlies; read from code). Call sites: `build_unified_timeline` (PIP branch), `build_dependency_entries` (warning condition), the local-tag early `continue` in `run_pin_checks`. Under "pin what's installed", the index must match where the installed build came from; when that can't be established, report the pin rather than pair it with the notebook's flag.

### Conda environments

- **C1. conda-forge OpenCV yields an uninstallable, wrong-variant pin and false "removed" and conflict findings.** conda-forge's opencv recipe writes stub dist-infos `opencv_python-{v}` and `opencv_python_headless-{v}` with only METADATA (the conda version, e.g. `5.0.0`) and INSTALLER (`conda`): no `direct_url.json`, no RECORD, so pip freeze prints plain `opencv-python==5.0.0` and the `file://` entry never catches them. `resolution.resolve_opencv_variant` checks headless first (`resolution.py` lines 435 to 442, confirmed), and the recipe installs both stubs in every build, GUI builds included, so the pin is always headless. The version is taken verbatim, but PyPI has only four-part releases (`5.0.0.93`), and `==5.0.0` doesn't match under PEP 440. Reviewer confirmed with `import cv2` and `cv2.imshow(...)`: pin `opencv-python-headless==5.0.0`, "[removed] ... no longer exists on PyPI" (it never existed), a false unresolvable-graph conflict, check exits 1 on every run, and the runner's install fails with "No matching distribution". The headless-first bias also hits pip users with both `opencv-python` and `opencv-python-headless` installed (common when two dependencies want different variants), giving the runner a build where `cv2.imshow` fails. Call sites: `resolve_opencv_variant`, `resolve_pypi_package_and_extras` (single-file and `--universal`), `build_writefile_tool_entries` (pins `opencv-python==5.0.0` via `IMPORT_TO_PYPI_MAP`), the wording in `drift.check_yanked_or_removed`. Fix: when the OpenCV distribution's INSTALLER is `conda`, map it to the newest PyPI release with the same first three components and tell the creator; choose the variant by build capability, not by which dist-infos exist.
- **C2. Conda-family install commands other than `conda install` produce no notice.** `magics.CONDA_INSTALL_PATTERN` matches only `(%conda|!conda|conda) install`. `!mamba install`, `%mamba install` (IPython 9 ships `%mamba` and `%micromamba`), `!micromamba install`, `!conda env update -f environment.yml` and the condacolab recipe (`condacolab.install()` then `!mamba install`, the standard Colab route for OpenMM and rdkit tutorials) all return zero notices, warnings and packages (reviewer confirmed; `!mamba install` and `%mamba install` reproduced). `!conda install --file requirements.txt` gets only the generic notice, while the pip `-r` equivalent gets a share-this-file warning. Fix: one table of conda front-ends (conda, mamba, micromamba, `%` and `!` forms) and subcommands (install, create, env create/update), with `--file`/`-f` handled like pip's `-r`.

### Pinning, delta and output stability

- **P4. Editable installs vanish without a warning.** `-e`/`--editable` is in `PIP_VALUE_FLAGS`, so pass 2 skips the flag and its path before the VCS/path check; `%pip install -e ./mypkg` yields no occurrence, no raw install and no diagnostic (confirmed). `-r` at least emits an `external_requirement` warning.
- **P6. Imports not found in the environment are labeled `pinned`.** `resolve_pypi_package_and_extras` returns status `pinned` for a not-found import rendered as a comment (confirmed: `baz` → `pinned`, `is_comment=True`), so JSON report consumers see a missing package as pinned.

### Code health

- **H1. Import parameters are typed `Any`, and result classes carry lossy tuple-unpacking shims.** Eight import parameters in `accelerator.py` and `resolution.py` are `Any`. `TimelineResult`, `ExtractionResult` and `HarvestResult` define `__iter__` for legacy unpacking; no production code uses it (the only unpacking is of `ExtractionResult` in `test_steady_py_fixtures.py`), and the shims convert `DiagnosticEvent` objects to strings. Remove the shims, migrate the tests, type the parameters. Same cleanup as G10 (only `process_package_requirements` is test-only).
- **H2. Broad `except Exception` hides logic errors.** About 20 production sites (accelerator, resolution, runtime, util, localmodules, scanning, drift). Two recorded bugs are exactly this: the swallowed `importlib.machinery` AttributeError and the swallowed extras `PackageNotFoundError`. Audit per site: narrow catches around our own and stdlib calls; keep broad catches around third-party probes (torch, TensorFlow, CUDA initialization), logged at debug with `exc_info`.

## Design gaps

- DG1. Optional dependencies that are never imported (openpyxl, gcsfs, spaCy models) are seen only if the notebook has an install line. There is no candidate detection. Package metadata can supply candidates without a hardcoded list: pandas declares openpyxl and gcsfs in its extras, so an imported package plus an installed package named in one of its extras is a candidate. spaCy models are declared in no metadata and need a different signal.
- DG2. There is no creator warning about guarded alternatives, and no runtime report of which alternatives are present. A clean run cannot verify the untaken branch. Partly addressed by Proposed features, "Install lines, creator declarations and manifest regeneration".
- DG3. It is unknown whether a platform baseline (Kaggle or Colab preinstalled packages) exists; candidate lists need one.
- DG5. Pins come from the interpreter running the CLI. If a creator installs steady-py with pipx or `uv tool`, or runs it from conda base while the kernel uses another env, every pin describes the wrong environment, and nothing warns (unverified lead; the natural next review boundary).
- DG6. No runtime policy for a pin whose public release matches the platform's but whose build tag differs (manifest `torch==2.8.0+cu121`, platform `2.8.0+cu126`). Accepting risks a CUDA mismatch; reinstalling means a multi-GB download over the platform build. The runtime counterpart of "pin what's installed"; needs an explicit decision.
- DG8. Offline installs of local wheels (`!pip install --no-index --no-deps /kaggle/input/<dataset>/<pkg>.whl`, the competition pattern for internet-off notebooks) get only a `raw_install` notice. The path exists only on Kaggle with that dataset attached, so the manifest records something another environment can't reproduce, and the package's version isn't tied to the pin. About 10% of Kaggle install lines in both eras of the corpus. Decided as matrix decision 11.
- DG7. The creator's own install lines run after Cell 2 and can undo its pins, and some lines Cell 2 cannot reproduce at all (guarded, computed, conda). Snapshot keeps every original cell (`generate.write_locked_notebook`, `generate.py` lines 406 to 407), so the runner executes Cell 2 and then the creator's install lines, after Cell 2 has printed "All N/N dependencies verified". Tested with pip 24.0 in a clean venv: `pip install -U tabulate` and a differing `==` moved a pinned tabulate, and installing `datasets` moved a pinned `requests` from 2.28.0 to 2.34.2 through the resolver. Addressed by Proposed features, "Install lines, creator declarations and manifest regeneration".

## Corpus evidence

`corpus_install_scan.py` over 11,767 unique Python notebooks (`install_lines4`, mostly Kaggle, sampled toward recent kernels) sets test priority by era. Comparing install lines in notebooks recording Python 3.10 or later with those recording 3.7 or earlier: guarded installs 14.6% against 3.6%, the `subprocess` list form 11.2% against 1.0%, `--no-deps` 11.5% against 4.1%, and variable requirements 6% against 1%. `%pip` stays under 6% on Kaggle in every era; `!pip` dominates. Range requirements (the version-operator bug) are 3% of recent Kaggle requirements but 19 to 29% in the cookbook-style collections. Undeclared optional dependencies are near universal where their signal appears: Styler without jinja2 in 344 of 344 notebooks, parquet without pyarrow in 217 of 227, Excel without an engine in 112 of 130. 82% of Kaggle notebooks install nothing, so a live-kernel bug that drops installed pins (K12) affects nearly every Kaggle notebook.

`corpus_install_scan.py` over `install_lines5` measured what replacing the line blanking with IPython's transform would change: of 1,108 cells blanking can't parse, the transform fixes 570, including all 67 valid-Python cells blanking corrupts, and breaks none. The 538 that fail either way are not valid Python (largely Python 2 and broken code). The same scan found 88 shell-joined or shell-conditional install lines in 35 notebooks (the Kaggle ones mostly `cd dir && pip install .`, local installs Cell 2 can't cover) and 123 install lines inside functions in 44 notebooks.

## Principles

- Cell 2 is not edited as text; changes go through the tool, which records their provenance. The tool will never infer every dependency, so the creator must be able to correct and extend the manifest: creator declarations are inputs to the tool, stored in the manifest with provenance, and read from their source by every snapshot. (Revises "Cell 2 is never hand-edited", which left manifest errors unfixable.)
- Report to the creator is the default for candidates and unknown targets. Never auto-add. Each report should be actionable through a creator declaration.
- Hard dependencies are out of scope. Optional dependencies are in scope. This holds only where pip installs the package and so resolves its dependencies; for a package the runner cannot install (an editable, the creator's own code), its `Requires-Dist` entries are in scope and are pinned from the installed environment.
- Comments and other display text are never a source of truth. Anything the tool needs later is a structured, hashed manifest field; anything it needs within a run is carried as a typed field, not parsed back out of rendered text.
- The recorded commit wins over a notebook's own unpinned VCS line. When the notebook installs `git+...@main` (or no ref) and the environment records a commit, pin the commit, consistent with pinning the installed version over an author's `>=` bound. This reverses the current development.md spec (a remote direct reference goes to `raw_installs` "unless the notebook's own install line names the same source"), which must be updated.
- Pin what's installed over what the notebook states loosely (an unpinned or `>=` line, an unpinned VCS line), with one exception: an explicit `==` in the notebook wins over the installed version, since that line runs after Cell 2 and installs its version anyway. Snapshot warns when the two differ.
- Each decision has one owner. Entry points (single file, batch, `--universal`, live kernel, check) differ only in how they gather inputs and render outputs, never in how they classify, resolve or judge. Most findings trace to decisions re-derived in several places; consolidation follows after more material is gathered.

## Reviewed and rejected

- Updating the manifest instead of rebuilding it: carrying forward values no current source states, with warnings on every snapshot and a `--rebuild` escape hatch. The losses it guarded against came from advising creators to delete redundant install lines, which took an index URL or an unimported package's pin with them. With that advice gone (install-lines spec, item 5.2), a value disappears only when the creator removes its source or the snapshot environment lacks it, and the delta reports either. Carrying would second-guess deliberate edits for little gain.

- `_RUN_CACHES` as a memory leak or thread hazard: caches are created once at import (four decorated functions) and nothing in the tool runs concurrently.
- `silence_fd2_stderr` swallowing other threads' output: intentional, and scoped to the brief CUDA probe window.
- Optional-dependency detection as a rabbit hole requiring a hardcoded knowledge base: the objection targets auto-adding, which the principles already exclude, and extras metadata supplies candidates without a hardcoded list.
- Unpinned packages evading drift checks: an install line without a version is pinned from the environment (`%pip install foo` became `foo==1.0`), and anything not installed becomes a comment, never a versionless dependency (confirmed). The underlying gap, statuses recorded only as comments, is already under Design gaps.
- Replacing `error: Optional[str]` on per-notebook results with Success|Failure types: most `Optional` fields are unrelated to failure (`delta` only when a manifest exists, `written_path` None when nothing was written), directory runs need one uniform per-notebook list, and the in-notebook API audience would face `isinstance` checks. Revisit before the first release if the API shape changes anyway.
- `is_prior_setup_cell` mixing read-phase analysis into the write phase: deciding which cells to replace requires reading them, and it parses only the cell under test with no scan state. Its real defects are K7 and K11.
- Keeping alternative pins per guard branch in Cell 2: Cell 2 would have to decide at run time which branch applies, which is too complex. Guarded install lines stay in the creator's code, and their packages are declared ignore (Proposed features, "Install lines, creator declarations and manifest regeneration").

## Proposed features

These features may affect or solve some of the issues listed in this document.

### Install lines, creator declarations and manifest regeneration

#### Problem

Snapshot puts Cell 2 at the top of the notebook and leaves the creator's own cells as they are. This causes three related problems:

1. The creator's install lines run after Cell 2 and can undo it. A `-U` upgrades a pinned package, a different `==` replaces it, and an unpinned package can move a pinned one through pip's resolver. By then Cell 2 has already printed "All N/N dependencies verified", so the message is false.
2. Some install lines can't be reproduced by Cell 2 at all:
   1. Guarded branches, such as `if IN_COLAB:` installs X and otherwise Y. Which branch applies is decided at run time, and Cell 2 can't predict it.
   2. Computed installs such as `%pip install $pkg`, where the package is decided by the notebook's own code, sometimes only after earlier cells run.
   3. Conda installs, requirement files, and packages that weren't installed when snapshot ran.

   These lines must stay in the notebook. Cell 2 can't pin them, and it can only verify one if it happens to be installed before Cell 2 runs.

3. Inference can't capture everything the creator knows. They may need a specific version or source that the environment doesn't reflect, or an optional dependency the code never imports. They may also be handling a package themselves and want steady-py to leave it alone.

steady-py can't safely edit the creator's code, especially on Kaggle and Colab. What it can do:

1. Tell the creator which install lines can undo Cell 2 and should be changed, and which ones Cell 2 already covers.
2. Tell them which lines must stay.
3. Give the creator a way to declare what they want: install this package (with a version or source), or ignore it because they handle it.
4. Round-trip those declarations through snapshot until the notebook's setup is fully accounted for.

#### Proposed solution

1. Declarations structure (working name `STEADY_PY_DECLARATIONS`; a better name is welcome):
   1. It is a tool-owned Python literal, parsed with `ast` and never executed. It is valid Python that does nothing when run. Parsing must handle any valid characters and comments.
   2. The literal is a list assigned to `STEADY_PY_DECLARATIONS`. Each entry is a dict whose first key names its kind and whose value names its subject, and every entry has a non-empty `reason`:

      ```python
      STEADY_PY_DECLARATIONS = [
          {"install": "acme-utils", "version": "2.1.0", "index_url": "https://pkgs.example.com/simple", "reason": "..."},
          {"ignore": "torch", "group": "gpu", "reason": "..."},
          {"accept": "numpy", "reason": "..."},
      ]
      ```

   3. Install, meaning "install this package": the package name, and optionally `version` (an exact version, installed as `==`), `extras` (a list), `url` (a direct reference such as a VCS URL with a commit or a wheel URL, never combined with `version`), `index_url`, `extra_index_url` and `find_links`. The index options become the manifest entry's `options` pairs. Without a `version` or `url`, the installed version is pinned, else PyPI's latest; with neither found, Cell 2 can't install it and snapshot warns.
   4. Ignore, meaning "I handle this": the package name, and optionally `version` (checked against what is installed, item 6.2) and `group` (a name tying guarded alternatives together).
   5. Accept, meaning "this finding is wrong for my notebook": a package or import name, exactly as the finding's message shows it, and nothing else. It covers every exit-1 finding for that name, at snapshot and at check, until the creator removes it (matrix decision 12). Each such finding's message prints the entry ready to paste.
   6. Package names compare in canonical form (PEP 503). An accept matches a finding's canonical package name or its import name.
   7. Every entry is validated before anything else runs. A literal that fails to parse, or an entry that isn't a dict, has no kind key or more than one, lacks a reason, has a key its kind doesn't take, has a value of the wrong type, or combines `url` with `version`, stops snapshot with exit 2, naming the cell or file, the entry and the problem. Continuing without it would pin every package the creator marked ignore. The message for an unknown key adds that a newer steady-py may be needed, since a declaration written for a newer version reads that way.
2. Where declarations come from:
   1. A declarations cell in the notebook, the default for online users. It persists in the notebook like any other cell. In a live kernel it is read from session history, where the last executed version counts; from the CLI it is read from the file. It must never match the prior-setup-cell rule, and snapshot warns if one cell holds both the declarations and the manifest.
   2. An optional declarations file with the same syntax, the natural route from the CLI and for collections. The API accepts it too. It is input only: nothing at run time needs it.
   3. An install and an ignore for the same package conflict, and so do two entries of one kind for one name. An accept never conflicts with an install or an ignore. Every conflict produces a warning, and the last one wins. The file is applied first and the notebook cell last, so the notebook wins, and within a single source the later entry wins. The winning entry replaces the other whole, with no field merging.
3. Round trip: snapshot reports proposals drawn from its diagnostics. Examples: guarded alternatives to confirm as ignore entries, values to list for a computed install, an optional extra to require. The creator edits the cell or file and runs snapshot again. Snapshot does not print the declarations back.
4. Validation and record:
   1. Snapshot checks each install entry. The package and version must exist, the version must support the notebook's Python, and it must resolve with the rest of the pins.
   2. Entries go into the hashed manifest with provenance, including which source each came from. A declarations file is recorded by a relative name or label, never a local path, since the manifest is shared.
   3. Snapshot reports drift, such as a declared package now detected on its own or a conflict with the environment.
   4. Cell 2 reads only the manifest. Check reads the manifest and the notebook's install lines (item 10.2).
   5. Every time a declaration changes an outcome, the run records an event naming the declaration (kind, name, origin) and what it changed: a finding that no longer counts toward exit 1, a package left unpinned, or a pin or source taken from an install entry. A conflict between entries is a warning instead (item 2.3). Snapshot and check print the events together as one "Declarations applied" section at the end of the report, and `--format json` carries them as structured events. An accept that matched nothing is listed there as no longer needed. Declarations take effect only through the one step that records the event, so no rule can act silently, and each rule's test asserts its event.
5. Install-line reconciliation, reported by snapshot and never applied to the creator's code:
   1. Packages Cell 2 installs, whether inferred or declared: each line naming one is conflicting (fix these first) or redundant. A line conflicts when, run after Cell 2 has installed `P==v`, it could leave P at another version or replace its distribution:
      1. Its specifier excludes v (`SpecifierSet.contains(v, prereleases=True)` is false).
      2. It upgrades (`-U`, `--upgrade`; uv `-U`, `-P P`) and its specifier admits any version other than v, a bare name included, whether or not a newer release exists yet.
      3. It reinstalls (`--force-reinstall`, `-I`/`--ignore-installed`; uv `--reinstall`), whatever the specifier, since this also reinstalls P's dependencies.
      4. It is a direct reference (URL, VCS, local path or wheel) that differs from the pin's recorded `url`, or any direct reference when the pin comes from an index.
      5. It is an editable naming P.
      6. It is a conda-family line naming P: conda ignores pip's installed state.

      Every other line naming P is redundant: pip finds the requirement satisfied and changes nothing, whatever its index options. A guard doesn't change the classification, only the advice (item 5.4). Computed and unreadable lines and `-r` files aren't classified, since their targets aren't known. Movement through dependencies needs no rule of its own: pip's default only-if-needed strategy leaves a satisfied requirement's dependencies alone, and a conflict between two pins is a resolver finding.
   2. For a conflicting line naming a package the notebook imports, the advice is to delete the line, or to remove the package from a line that installs others too; the import keeps the pin alive. For a package nothing imports, the advice is to replace the line with an install declaration, since the next snapshot would otherwise drop the pin. A redundant line gets no advice and is reported as information: Cell 2 already installs the package and the line changes nothing. Keeping it costs one satisfied pip call, and the next snapshot still harvests its options, such as an index URL.
   3. Packages declared ignore: the line is always kept, with no advice.
   4. Lines Cell 2 doesn't reproduce and the creator hasn't declared (guarded branches, computed installs, conda, `-r`, packages not installed at snapshot): the line is kept, and snapshot proposes a declaration for it.
   5. Lines that don't install into the kernel (`-t`/`--target`, installs into a remote sandbox such as `sandbox.commands.run("pip install ...")`) get no advice.
   6. Each line is located by quoting its text, with the cell position and nearest heading as hints. Advice and declaration proposals come out as one list.
   7. The classification assumes Cell 2 runs before the creator's install lines. An unpinned line that runs first installs the latest release and its dependencies; Cell 2 then restores the pin but not the dependencies. When a notebook file holds Cell 2 below a cell with an install line (setup cells pasted lower down), snapshot and check warn that Cell 2 must be the first code cell. A live session has no cell positions, so there it rests on the paste instructions.
6. Cell 2 behavior:
   1. It installs pins and install declarations, and never installs or pins ignored packages.
   2. An ignored package that is already installed is checked against its pin if it has one, and otherwise noted as present. A mismatch is reported as information, not failure: guarded alternatives differ by platform, and the creator's own line may replace the version after Cell 2 runs.
   3. An ignored package that isn't installed yet is reported as installed later by the notebook, and counts neither for nor against "N/N verified".
   4. pip can still install or move an ignored package as a dependency of a pinned one. Snapshot warns when an ignored package is reachable from the pins' dependency graph.
   5. For a pinned package whose conflicting line the creator left in place (`packages.conflicting_line`), the "N/N verified" line names it as one a later cell can change.
7. Limitation: a creator may forget to remove the snapshot call before sharing the notebook, and snapshot then runs whenever someone else runs the notebook. It never writes to the notebook, so the author's setup cells are unaffected. Snapshot returns immediately in Kaggle "Save Version" runs, and skips its slow checks when nothing has changed (Snapshot manifest regeneration, item 4). Otherwise it can't tell the creator from anyone else, so its output begins: "This output is for the notebook's author. If you are running someone else's notebook, ignore it and don't paste anything from it; you can delete this cell."
8. Ownership:
   1. Resolution decides what Cell 2 covers.
   2. One parser reads the declarations from every source.
   3. One step applies declarations and records each effect (item 4.5).
   4. One pure function classifies install lines, shared by snapshot and check.
   5. The entry points differ only in how they gather input.
9. Prerequisites:
   1. "Single pip flags and raw-install index flags are dropped" and "Parse pip arguments the way pip does".
   2. "In a live kernel, no install line, conda command or `%%writefile` script is harvested".
   3. "An install line with extras produces an invalid pin".
   4. Cell positions by notebook order: "Batch reports lose each notice's notebook, and cell numbers match nothing the user sees", plus execution-order scanning, which discards each cell's position (`scanning.get_ordered_code_cells`).
   5. Guard detection, so guarded lines never get delete advice: done (G3, G6, G9), apart from one-line shell conditionals (G5).
10. Decisions:
    1. A conflicting line makes snapshot exit 1, and a redundant line is information only (exit 0). An accept or ignore declaration overrides the exit (matrix decision 12).
    2. Check also classifies the notebook's install lines against the manifest's packages, through the same function: conflicting lines exit 1, redundant ones are notices. Check gives no delete-or-replace advice, since that needs the import join and so the environment.
    3. Snapshot records each pinned package with a conflicting line left in place (`packages.conflicting_line`), and Cell 2 warns the runner (item 6.5). Cell 2 can't see later cells, so the manifest is the only mechanism.
    4. With `--output`, advice targets the source, as in every mode, and notes that once the lines are deleted the source installs nothing without the companion. The companion is regenerated from the source on every snapshot, so edits to it are lost.
11. Open, optional: on Colab only, read the live notebook through `google.colab._message.blocking_request('get_ipynb')`. It would fix the unexecuted-cell, deleted-cell and cell-position problems of the live path. It is a private API (used by colab2pdf and wandb), and no Kaggle equivalent was found.

#### Snapshot manifest regeneration

Problem: snapshot compares its new manifest with the previous one only where it reads one, the source file. Under `--output` the source holds no manifest, and a live session reads none, so those runs report no delta and date every manifest as just changed.

Behavior:

1. Every snapshot builds the manifest from its current sources only: the declarations, the notebook text and the environment. Nothing is carried from the previous manifest except change dates (`delta.settle`). A value disappears when its source does, through the creator's edit or a snapshot environment that lacks it, and the delta reports it on that run.
2. The previous manifest is read in every mode, as the comparison for the delta and the dates:
   1. A file: from the source.
   2. Under `--output`: from the file the write replaces, else the source.
   3. A live session: from the most recently executed Cell 2 in session history, through the same literal reader and hash check. With none, the report says no setup cell has run in this session, and the run is a first snapshot.
3. Reporting: the existing delta, covering every manifest field. A declaration removed from its cell, or from a declarations file that wasn't passed, is a removal like any other. A snapshot that changes nothing writes nothing (matrix decision 3).
4. Slow checks: when the packages (`custom_sourced` aside), Python version and declarations match the previous manifest, snapshot reuses its baseline and `custom_sourced` values and skips the PyPI checks. Check still reports anything that changed on PyPI since.
5. Safety: a live session never writes to the notebook. Only an explicit author action replaces the manifest.
