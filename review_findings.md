# Review findings (verified, pending entry into development.md)

## Known bugs

- **One IPython line anywhere breaks manifest extraction for the whole notebook.** `generate.extract_manifest_from_file` joins every code cell into one source and calls `ast.parse` once, after blanking lines that start with `%` or `!`. A single `files = !ls`, `x = %timeit ...` or `df?` survives the blanking and fails the parse, so the notebook returns "Could not parse" and check and delta break (confirmed with a two-cell notebook). The blanking itself also turns valid Python invalid: a triple-quoted string whose closing line starts with `%`, a backslash continuation line starting with `% `, and a parenthesized condition whose last line starts with `!= b)` all parse before stripping and fail after (tested). Fix: parse per cell (the manifest lives in one cell), and replace the blanking with one shared helper.
- **A scan silently loses every import in a cell it can't parse.** `scanning.py` applies the same line-blanking (copy-pasted twice, a third copy is in `generate.py`) and, on `SyntaxError`, drops the cell with no diagnostic. A notebook with one magic in expression position loses that cell's imports while the report looks complete. This is false success; at minimum emit a diagnostic naming the cell.
- **A dropped connection during a PyPI fetch crashes the run.** `pypi._fetch_pypi_json` reads the response inside the try, but catches only `HTTPError`, `URLError`, `TimeoutError` and `JSONDecodeError`. Errors raised during the read (`http.client.RemoteDisconnected`, `IncompleteRead`, SSL errors) escape, so one transient drop exits 2 instead of reporting `NETWORK_ERROR`. Fix: catch `OSError` (which already covers `URLError` and `TimeoutError`) and `http.client.HTTPException`.
- **Local-module detection depends on an incidental import.** `localmodules._found_in_dir` calls `importlib.machinery.PathFinder`, but the module imports only `importlib.util`, which does not bind `importlib.machinery` (AttributeError in a clean 3.12 interpreter). It works today only because `installed.py` imports `importlib.metadata`. If that changes, the `except Exception` swallows the error and every local module silently reports as not found. Fix: `import importlib.machinery`.
- **Transitive checks evaluate platform markers against the machine running check.** `drift._marker_environment` overrides only the Python version and extra and takes the rest from `default_environment()`. Running check on Windows against a Kaggle or Colab notebook drops Linux-only requirements (torch's `nvidia-*` dependencies are marked `platform_system == "Linux"`) and includes Windows-only ones. Fix: set `sys_platform`, `platform_system`, `os_name` and `platform_machine` from the target when it is Kaggle or Colab; keep the host values for a local target.
- **OpenCV variant detection has its own view of what's installed.** `resolution.resolve_opencv_variant` runs `pip list` in a subprocess on every call, unmemoized, even though the caller already holds `frozen_env` from the run's single `pip freeze`. Two independent sources of installed state can disagree. Fix: derive the variant from `frozen_env`.
- **Replacing a prior setup cell can discard user code.** `generate.is_prior_setup_cell` matches any code cell that assigns `STEADY_PY_MANIFEST` anywhere, including inside a function (`ast.walk`), and `write_locked_notebook` drops the whole cell with no warning. With `--in-place` a user's scratch cell that copied the assignment is lost from the original. The content match is deliberate (untagged pasted cells must be replaced), so the fix is a warning when a removed untagged cell contains other statements, not dropping the match.
- **A package that can't be looked up becomes a confirmed conflict.** `drift.resolve_transitive_graph` excludes root pins not found on PyPI, but `_PyPIResolutionProvider.find_matches` returns no candidates for any transitive package whose fetch status isn't FOUND. Resolvelib then raises `ResolutionImpossible`, reported as a CONFIRMED conflict. Triggers: a transitive dependency hosted only on a custom index (NVIDIA's index packages), or, more likely, a transient network error on any transitive fetch. "Could not look it up" should be reported as unverifiable.
- **Extras promotion is nondeterministic and records at most one extra.** `resolution.resolve_pypi_package_and_extras` iterates the submodule `set` and stops at the first tail name that matches a `Provides-Extra`, so with two matches the chosen extra depends on hash randomization and can differ between runs. Name matching also misses most extras, since extras rarely share names with submodules, and pip does not record which extras were requested at install time. A sounder heuristic: an extra counts as installed if its `Requires-Dist` entries are all present.
- **Display text is parsed back as data.** `analyze.analyze_batch_repository` recovers a package name from `dep.comment_text.split()[1]` when `dep.name` is empty, and `generate.py` filters auxiliary entries with `aux.comment_text.startswith("\n# ---")`. Both are strings the tool built earlier in the same run, so they can't be tampered with, but rewording a comment would silently misfile packages. Carry structured fields (name, status) instead of parsing rendered text.
- **The setup markdown cell is recognized by its heading text.** `generate.is_prior_setup_cell` falls back to matching `SETUP_MARKDOWN_HEADING`, which is unprotected notebook text. If a user edits the heading and the cell has lost its managed tag, the old setup cell survives as a stale duplicate. Low severity: the managed tag is the primary signal.


### Guards and install harvesting

- **A guarded install line erases every import in its cell.** In a cell containing `import pandas` and `if IN_COLAB:` followed by an indented `%pip install xyz`, the line blanking leaves an empty if-body, `ast.parse` raises `SyntaxError`, and the scan returns zero imports for the cell with no diagnostic (confirmed by running `scanning.extract_import_occurrences_from_source` and `extract_imports_from_sources_full`). The standard guarded-install pattern silently removes real dependencies.
- **A guarded import loses its guard when the pip name differs.** `resolution.build_unified_timeline` computes `is_guarded = pkg_name in guarded_set`, where `pkg_name` is the install line's pip name (`python-dotenv`, `scikit-learn`) and `guarded_set` holds import names (`dotenv`, `sklearn`). The lookup never matches, so the package is installed although its import is guarded (verified by running). The same key mismatch drops submodules (`submodules_map` is keyed by import name), so extras promotion never fires for such packages.
- **A guarded install line is installed unconditionally.** `magics.harvest_pip_install_occurrences` matches lines with a regex and has no scope information, so `if IN_COLAB: %pip install x` is treated as a top-level install (verified by running). Raw installs and index URL flags are harvested the same way, regardless of guard (read from code).
- **A variable install becomes a package named `$pkg`.** `%pip install $pkg` is harvested literally (verified by running). A static scan cannot know the value; this should be a warning, not a package.
- **Several install forms are not detected, and nothing warns.** `!python -m pip install`, `!{sys.executable} -m pip install`, `os.system(...)`, `subprocess` calls and `get_ipython().system(...)` are all missed (verified by running). `PIP_INSTALL_PATTERN` recognizes only `%pip`, `!pip` and bare `pip`/`pip3`.
- **Mutually exclusive branches collapse to the last pin.** `magics.resolve_pip_occurrences` is last-wins by canonical name, which is correct for sequential reinstalls but wrong when two branches install the same package with different pins or flags; only a warning remains (read from code).
- **Non-literal dynamic imports get a generic warning with no guard state.** Only `importlib.import_module` (including aliased bindings) and `__import__` are recognized (read from code).
- **Guard tagging is coarse.** `TYPE_CHECKING`, `if __name__ == "__main__"` and platform flags are treated like `try/except ImportError`, and alternatives have no group identity or intent class (read from code).
- **A wrapper helper that shells out to pip loses the guard at its call site** (read from code).
- **A second, test-only resolution path carries its own guard logic.** `resolution.build_manifest_entries`, `build_dependency_objects` and `process_package_requirements` are called only from tests, and duplicate the guard and resolution logic of `build_unified_timeline`. Tests pass against code production never runs. Remove them or move their tests onto the live path.
- **`--opt=value` pip flags are silently dropped.** `magics.harvest_pip_install_occurrences` splits arguments on spaces and matches index flags exactly, so `--index-url=https://...` and `--extra-index-url=...` fail the match and are then skipped as generic flags. Both it and `harvest_index_urls_from_sources` return no URL (confirmed); the space-separated form works. Cell 2 then searches public PyPI and fails.
- **PEP 508 direct references are split into three entries.** `%pip install "pkg @ git+https://..."`, the form pip accepts, yields packages `pkg` and `@` plus a detached raw install of the URL, because `split()` runs before quotes are handled (confirmed). The unquoted form is a pip error and should be flagged, not registered.
- **`%%writefile` cells with leading blank lines are scanned as notebook code.** `scanning.classify_cell_source` checks only the first line, so a blank first line makes the cell PYTHON and its imports (`import torch` in the test) become notebook dependencies (confirmed). IPython's `TransformerManager` strips leading blank lines and runs the cell as `run_cell_magic('writefile', ...)`, so IPython accepts this form.

### Cell 2 runtime (`runtime.install`)

- **Pins with extras never pass the already-installed check.** A promoted name such as `packaging[foo]` is written to the manifest as-is, and `importlib.metadata.version("packaging[foo]")` raises `PackageNotFoundError` (confirmed). The `except Exception: pass` hides it, so pip reruns on every execution, `any_install_performed` fires the restart warning, and the package never enters the drift baseline. Stripping the brackets is not enough: the base package being present doesn't mean the extra's dependencies are. Either check the extra's `Requires-Dist` entries or let pip handle bracketed names (pip is idempotent and correct for extras).
- **A pin that drifts after being verified still counts as verified.** If package A passes and a later install changes its version, the loop prints a drift line, but `passed_count` still includes A and the summary reads "Setup complete! All N/N dependencies verified." This is false success. Packages outside the manifest (for example, a platform package an install downgrades) aren't tracked at all, because the baseline holds only manifest packages already visited. Fix: snapshot `importlib.metadata.distributions()` before and after the loop, report the diff, and re-verify every manifest pin before printing the success line. The same fix covers raw installs that move pinned versions after they were verified.

### Creator environment capture

- **A failed `pip freeze` produces an empty "verified" manifest and exit 0.** On a nonzero return code, `installed.get_installed_environment` returns `({}, [])`, indistinguishable from an empty environment, and skips the PEP 610 overlay; the only signal is a `logger.warning` that `--quiet` suppresses. Every import becomes a "not found" comment, Cell 2 shows `'dependencies': []` under "VERIFIED ENVIRONMENT DEPENDENCIES", and the runner sees "All 0/0 dependencies verified." Triggers: a uv venv (no pip module; confirmed by the reviewer), a UnicodeEncodeError on a non-ASCII editable path under a Windows ANSI code page (simulated), and pip's own freeze crashes (pip 20.2.x raised AssertionError on flit editables). `results.Environment` has no failure field. Fix: a typed failure carrying pip's stderr; endpoints map it to exit 2 with nothing written. Call sites: `get_installed_environment`, `endpoints.detect_environment` (scan, snapshot, batch), `results.Environment`.
- **Packages frozen as `name @ file://...` are dropped, even when that version is on PyPI.** `split_frozen_pin` returns version `None` for every `@` pin, and `resolve_pypi_package_and_extras` sends local URLs to a `system_path` comment (confirmed: `six @ file:///...whl` pinned nothing; the reviewer saw "STATUS: Clean", exit 0, no warnings). Verified real-world trigger: conda-built packages carry `direct_url.json`, so pip freeze in a fresh Miniconda env lists e.g. `certifi @ file:///opt/conda/conda-bld/...` (conda/conda#11580), and core packages vanish for Anaconda creators. Windows Anaconda shows the same pattern as `file:///C:/b/abs_.../croot/<pkg>_.../work` (second reviewer, confirmed through `generate.apply_output_to_notebook`: only the conda-built package vanished, Cell 2 told the creator to "publish" sympy, and the validation report carried no finding or notice). Fix: carry the installed version with the URL. Detect conda-built packages (the env's `conda-meta/` records are ground truth; the dist-info `INSTALLER` file likely reads "conda", unverified) and pin those as name==version with a notice. An unexplained local `file://` reference is reported to the creator as a candidate, not auto-pinned, since a private project can share a PyPI name. Call sites: `split_frozen_pin`, `get_installed_environment`, `_read_direct_reference_pins`, both branches of `resolve_pypi_package_and_extras`, `build_auxiliary_tool_entries`, `build_writefile_tool_entries`.
- **The direct-reference overlay can replace the active package's pin with a shadowed copy's.** `_read_direct_reference_pins` walks `distributions()` across all of `sys.path`, skips distributions without `direct_url.json`, and `setdefault`s among the rest; `get_installed_environment` then applies `frozen.update()` unconditionally. Import and pip use the first copy on `sys.path`; this code keeps the first copy that has `direct_url.json`. Reviewer confirmed: six 1.17.0 active (import, `importlib.metadata`, pip freeze all agree) recorded as a shadowed `six @ file:///...1.16.0`. With a remote URL the stale source goes into `raw_installs` and the runner installs the old version. Real-world trigger (untested): an all-users Anaconda install where pip falls back to the user site. Another second source of installed state. Fix: mark every canonical name on first sight, with or without `direct_url.json`, and ignore later duplicates. The overlay also replaces lines pip freeze already formatted correctly: diffed against pip 24.0's `direct_url_as_pep440_direct_reference`, ours drops `#subdirectory=` and archive hashes (`#sha256=`; the code has no hash handling). If freeze is kept, the alternative fix is to let freeze's lines win and fill only names it cannot express (editables).
- **`--full-freeze` embeds private local paths in the shared notebook.** `get_installed_environment` returns freeze output verbatim, and `generate` `repr()`s it into `FULL_FREEZE_FALLBACK`: editable paths (`-e /Users/.../ClientAcme/...`) and `file://` URLs land in Cell 2 (reviewer confirmed). This breaks the development.md promise that no private path leaks into a shared notebook. The list sits outside the hashed manifest, and `runtime.py` never reads it despite the "FALLBACK" name (confirmed). Consider removing the flag rather than sanitizing it; otherwise build the list from parsed entries, reducing local references to name==version with a note.
- **VCS direct references lose `#subdirectory=`.** `_read_direct_reference_pins` builds `vcs+url@commit` and ignores the `subdirectory` key of `direct_url.json` ("subdirectory" appears nowhere in the code). The runner installs the repository root, which fails or installs a different project. `_direct_source_key` also strips the fragment, so `same_direct_source` and the merge loop in `generate.generate_production_blueprint` treat two packages from different subdirectories of one monorepo as one source and drop the second (confirmed by a second reviewer: `raw_installs` held only `alpha`, `runtime.install` printed "All 1/1 dependencies verified" and `beta` was not importable; `TestSameDirectSource` has no subdirectory case). This also hits the common Kaggle pycocotools install from cocoapi (`#subdirectory=PythonAPI`) whenever the notebook lacks its own install line. Fix: append `#subdirectory=` when present and include it in the source key, while still ignoring ref, egg and hash.
- **Non-PEP 440 versions are stored with a stray `=`.** Freeze prints `legacypkg===0.8.1ubuntu1` (still true in pip 26.2.1), and every `split("==", 1)` stores the version as `=0.8.1ubuntu1`. Low harm. Call sites: `get_installed_environment`, `split_frozen_pin`, `resolution.py` (two sites).
- **A directory scan tells the creator that installed git and conda packages are missing.** `analyze.analyze_batch_repository` sends every comment entry except `platform_pseudo_module`, `build_tool` and `local_module` into `missing_packages`, so direct-reference and `system_path` packages are reported as "not found installed ... run 'pip install <package>'" by `reporting.format_console_report` (called from `cli.run_scan_directory`) and `format_json_batch_report`. Following that advice replaces a git build with whatever PyPI hosts under the name. Confirmed for the analysis (`missing_packages == {'zzq-remote': ..., 'sympy': ...}`); console text read from code. Root cause: batch re-derives meaning from `is_comment` plus an exclusion list instead of the status, the batch-versus-single drift pattern again. Fix: an explicit status-to-bucket mapping with a "non-PyPI source" bucket.
- **Cell 2 comments claim a direct-reference package "is installed from the non-standard sources list" when nothing installs it.** `installed.direct_reference_note` hardcodes the clause, and it is called from four places (`resolution.py` lines 157, 215, 305, 333: auxiliary tool, `%%writefile` script, guarded, direct reference), but only direct-reference entries reach `raw_installs` (confirmed by a second reviewer; the existing guarded test asserts `raw_installs` is empty). False user-facing text, worst for `%%writefile` scripts later run via `!python train.py`. Fix: the note states provenance only; the installation clause comes from the code that actually adds the spec.

### Pinning, delta and output stability

- **Version operators are stripped into invalid or untested pins.** `resolution.build_unified_timeline` computes `v_clean = occ.version_spec.lstrip("=<>!~")` and the manifest writes `==`. `%pip install torch>=2.0,<3` becomes `torch==2.0,<3` (an invalid specifier), and `numpy~=1.26` becomes `numpy==1.26` although 1.26.4 is installed (confirmed). Preserving the author's bounds would defeat reproducibility. Pin the installed version when it satisfies the author's spec (`packaging.specifiers.SpecifierSet`), report when it doesn't, and keep an explicit `==` as written.
- **An import resolves to an arbitrary distribution when several provide its top-level name.** `resolve_pypi_package_and_extras` takes `pkg_dist_map[imp][0]`, and `imp` is the top-level module. For namespace packages this is plainly wrong: `from google.cloud import storage` pinned `protobuf` (confirmed). Two installed variants of one module also occur in practice (three distributions provide `cv2` in a stock container; only the separate OpenCV path handles that case). Resolve against the full dotted import using `dist.files`, and report when the match is still ambiguous rather than pick one.
- **Delta ignores everything but name and version.** `delta.compute_delta` compares name to version, Python, GPU and baseline only, so changes to flags (`--extra-index-url`, `--find-links`), `raw_installs`, `custom_sourced` and `local_modules` report "no changes" while the manifest is rewritten (read from code).
- **Editable installs vanish without a warning.** `-e`/`--editable` is in `PIP_VALUE_FLAGS`, so pass 2 skips the flag and its path before the VCS/path check; `%pip install -e ./mypkg` yields no occurrence, no raw install and no diagnostic (confirmed). `-r` at least emits an `external_requirement` warning.
- **Snapshot rewrites an unchanged notebook.** `create_managed_cells` assigns random cell IDs (`uuid.uuid4()`), and `generated_at`, and therefore `dependency_hash`, change on every run, so an in-place snapshot of an unchanged notebook always produces a diff. Fix: reuse existing managed cell IDs, and either skip the write when the delta is empty or carry `generated_at` forward. Which depends on what `generated_at` is meant to record.
- **Imports not found in the environment are labeled `pinned`.** `resolve_pypi_package_and_extras` returns status `pinned` for a not-found import rendered as a comment (confirmed: `baz` → `pinned`, `is_comment=True`), so scan JSON consumers see a missing package as pinned.

### Code health

- **Import parameters are typed `Any`, and result classes carry lossy tuple-unpacking shims.** Eight import parameters in `accelerator.py` and `resolution.py` are `Any`. `TimelineResult`, `ExtractionResult` and `HarvestResult` define `__iter__` for legacy unpacking; no production code uses it (the only unpacking is of `ExtractionResult` in `test_steady_py_fixtures.py`), and the shims convert `DiagnosticEvent` objects to strings. Remove the shims, migrate the tests, type the parameters. Same cleanup as the test-only resolution path.
- **Broad `except Exception` hides logic errors.** About 20 production sites (accelerator, resolution, runtime, util, localmodules, scanning, drift). Two recorded bugs are exactly this: the swallowed `importlib.machinery` AttributeError and the swallowed extras `PackageNotFoundError`. Audit per site: narrow catches around our own and stdlib calls; keep broad catches around third-party probes (torch, TensorFlow, CUDA initialization), logged at debug with `exc_info`.
- **The package logger never propagates, even as a library.** `__init__.py` sets `propagate = False` at import, so a host that configures only the root logger gets nothing from steady-py (a host can still attach handlers to the `steady_py` logger directly). The stated reason, avoiding double printing, applies only once the CLI attaches its console handler. Move `propagate = False` into `configure_console()`.

## Design gaps

- Optional dependencies that are never imported (openpyxl, gcsfs, spaCy models) are seen only if the notebook has an install line. There is no candidate detection. Package metadata can supply candidates without a hardcoded list: pandas declares openpyxl and gcsfs in its extras, so an imported package plus an installed package named in one of its extras is a candidate. spaCy models are declared in no metadata and need a different signal.
- There is no creator warning about guarded alternatives, and no runtime report of which alternatives are present. A clean run cannot verify the untaken branch.
- It is unknown whether a platform baseline (Kaggle or Colab preinstalled packages) exists; candidate lists need one.
- Guard, unresolved and install-only status exist only as Cell 2 comments; the manifest has no protected record of them. `check` and the planned report of which guarded alternatives are present need them as manifest fields.
- Pins come from the interpreter running the CLI. If a creator installs steady-py with pipx or `uv tool`, or runs it from conda base while the kernel uses another env, every pin describes the wrong environment, and nothing warns (unverified lead; the natural next review boundary).
- A genuinely local `system_path` dependency produces no console warning and exit 0 (unverified lead from the environment-capture review).

## Principles

- Cell 2 is never hand-edited. Creator declarations are inputs to the tool.
- Report to the creator is the default for candidates and unknown targets. Never auto-add.
- Hard dependencies are out of scope. Optional dependencies are in scope.
- Comments and other display text are never a source of truth. Anything the tool needs later is a structured, hashed manifest field; anything it needs within a run is carried as a typed field, not parsed back out of rendered text.
- The recorded commit wins over a notebook's own unpinned VCS line. When the notebook installs `git+...@main` (or no ref) and the environment records a commit, pin the commit, consistent with pinning the installed version over an author's `>=` bound. This reverses the current development.md spec (a remote direct reference goes to `raw_installs` "unless the notebook's own install line names the same source"), which must be updated.

## Proposed fixes

- **Parse magics into Python, then scan one AST.** Transform `%` and `!` lines, `x = !cmd` and `obj?` into `get_ipython()` calls before parsing. IPython's `TransformerManager` (`IPython.core.inputtransformer2`) does this; IPython is not a base dependency, so use it when importable and fall back to a small transformer of our own. Install commands then inherit the guard state of their enclosing block. Also fixes the stripping bugs above and replaces the three copies of the blanking code.
- **Join pip names to import names through installed metadata.** Use the run's `packages_distributions()` (`pkg_dist_map`) first and `IMPORT_TO_PYPI_MAP` as a fallback, so guards and submodules carry across name differences. Decide which wins when an unconditional install meets a guarded import (the defect above implies the guard does).
- **Harvest literal shell-outs; warn on the rest.** After the AST change, `os.system`, `subprocess` and `get_ipython().system` calls with literal pip arguments are recordable with their guard state. Emit a `DiagnosticEvent` only for non-literal arguments, including `%pip install $pkg` and non-literal dynamic imports.
- **Parse pip arguments the way pip does.** Tokenize with `shlex.split`, use an option table that accepts both `--opt value` and `--opt=value`, and parse requirement tokens with `packaging.requirements.Requirement` (already a base dependency). The magics-to-AST change doesn't cover this, since `run_line_magic` still receives the raw argument string.
- **Read installed state from `importlib.metadata`, not `pip freeze` text.** One source, first match on `sys.path` wins, versions always carried (including for direct references), PEP 610 data read directly. Addresses the failed-freeze, `file://`, shadowing, `#subdirectory=` and `===` bugs at the root, and removes the dependency on pip being present. Freeze output has changed across pip releases (direct references as `name @ url` since 20.1; setuptools and wheel no longer excluded on Python 3.12+ since 24.1; legacy versions deprecated in 24.1), so parsing it ties results to the creator's pip version. Precondition: differential testing against `pip freeze` on the Docker tiers (plain 3.11, Kaggle, Colab), a conda env and a uv env, accounting for every difference (freeze's exclusions, name spelling, shadowing order, legacy `.egg-link` editables) before switching. The new reader is a second implementation of pip's internal `direct_url_as_pep440_direct_reference`, so it must reproduce VCS commit, `#subdirectory=` and archive-hash formatting, and the differential test must include direct references (VCS with subdirectory, archives with hashes, conda-built `file://`, editables). Keep freeze afterward as a test oracle only.
- **Deferred: keep alternative pins per branch.** Cell 2 installs one environment, so keeping both pins needs a way to say which branch applies at runtime. Depends on guard identity and creator declarations; until then, report to the creator.

## Reviewed and rejected

- `_RUN_CACHES` as a memory leak or thread hazard: caches are created once at import (four decorated functions) and nothing in the tool runs concurrently.
- `silence_fd2_stderr` swallowing other threads' output: intentional, and scoped to the brief CUDA probe window.
- Optional-dependency detection as a rabbit hole requiring a hardcoded knowledge base: the objection targets auto-adding, which the principles already exclude, and extras metadata supplies candidates without a hardcoded list.
- Unpinned packages evading drift checks: an install line without a version is pinned from the environment (`%pip install foo` became `foo==1.0`), and anything not installed becomes a comment, never a versionless dependency (confirmed). The underlying gap, statuses recorded only as comments, is already under Design gaps.
- Replacing `error: Optional[str]` on per-notebook results with Success|Failure types: most `Optional` fields are unrelated to failure (`delta` only when a manifest exists, `written_path` None when nothing was written), directory runs need one uniform per-notebook list, and the in-notebook API audience would face `isinstance` checks. Revisit before the first release if the API shape changes anyway.
- `is_prior_setup_cell` mixing read-phase analysis into the write phase: deciding which cells to replace requires reading them, and it parses only the cell under test with no scan state. Its real defects are recorded under Known bugs.
